# 시험 배포 규격

결론: 시험 날 자료(문항 구성과 배점, 정답, 유형 분류, 등급컷, 풀이 잠금 달력)는 앱을 새로 내지 않고 발행물로 내요. 팀이 발행 도구(`npm run exams:*`, scripts/exams)로 원본을 검사하고 Ed25519 로 서명해 발행물을 만들고, 정해진 주소 한 곳에 올려요. 아이폰 앱 껍데기가 그 주소에서 발행물을 받아 서명과 SHA-256 을 확인한 뒤 다리 규격 2의 remote 로 웹에 넘기고, 웹은 넘겨받은 시험을 다시 검사해서 써요. 이 문서는 작업 지시서 3의 6-2(발행물 형식)와 6-3(받는 쪽 규칙)을 옮기고, 발행 도구가 실제로 지키는 세부, 다리 규격 2와의 관계, 고정 주소가 갖춰야 할 조건을 더한 것이에요. 받는 쪽 규칙은 작업 지시서 4(아이폰 껍데기)가 구현해요. 주소는 아직 정하지 않았어요(사람이 정해요).

사람이 따라 하는 발행 순서는 docs/시험_당일_순서.md, 시험 파일의 칸은 docs/시험_추가_방법.md, 껍데기와 웹의 약속은 docs/앱_다리_규격.md 에 있어요. 이 문서의 값(시험 id, 날짜, 시각, seq)은 모두 형식 예시예요.

## 1. 흐름

1. 사람이 원본을 고쳐요: exam-data/src/<시험 id>.json(원본 시험 파일), exam-data/locks.json(풀이 잠금 달력).
2. `npm run exams:check` 가 원본을 검사하고 마지막 발행 기록(exam-data/state.json)과 견줘요. 아무것도 쓰지 않아요.
3. `npm run exams:publish` 가 같은 검사를 통과하면 seq 를 올려 발행 폴더(dist-exams)를 새로 만들고 index.json 에 서명하고 state.json 을 고쳐요.
4. `npm run exams:verify` 로 발행 폴더를 확인하고, 정해진 주소에 올린 뒤 그 주소로 한 번 더 확인해요.
5. 껍데기가 주소에서 받아 3장의 규칙대로 확인하고, 통과한 자료만 기기에 보관하고 웹에 넘겨요(4장).
6. 웹은 넘겨받은 시험을 하나씩 다시 검사하고 묶음 안 시험과 합쳐요.

앱이 그 주소로 보내는 것은 없어요. 받기만 해요.

## 2. 발행물 형식(작업 지시서 3의 6-2)

발행 폴더 하나가 발행물 하나예요. 매번 원본의 모든 시험을 담는 전체 발행이고, exams:publish 가 발행 폴더를 통째로 새로 만들어서 그 전 발행의 파일이 남지 않아요.

```
dist-exams/
  index.json                   발행 목록
  index.json.sig               index.json 의 서명
  files/<시험 id>.<rev>.json   시험 파일(시험마다 하나)
```

### 2-1. index.json

모양은 `{ format, seq, issuedAt, exams, locks }` 예요.

| 칸 | 값 | 뜻 |
| --- | --- | --- |
| format | 1 | 발행물 형식 번호. 지금은 1뿐이에요 |
| seq | 1 이상의 정수 | 발행 번호. 발행할 때마다 1씩 커져요(state.json 의 seq + 1). 발행 도구는 1부터 내요 |
| issuedAt | "YYYY-MM-DDTHH:mm" | 발행 시각(한국 시간, 분까지). 마지막 발행보다 이르지 않아요. 앱의 시험 선택 화면에 "받은 자료 기준"으로 나와요 |
| exams | 배열 | 시험마다 { id, rev, file, sha256 } 하나. id 차례예요 |
| exams 의 id | 글자 | 시험 id. 영어 소문자와 숫자를 붙임표(-)로 이은 모양이에요 |
| exams 의 rev | 1 이상의 정수 | 그 시험 파일의 판 번호. 시험 파일 안의 rev 와 같아요 |
| exams 의 file | 글자 | index.json 이 있는 곳 기준의 상대 경로. 발행 도구는 files/<id>.<rev>.json 으로 적어요(형식 예시: files/exam-id.3.json) |
| exams 의 sha256 | 글자 64자 | 그 파일 바이트의 SHA-256(16진수 소문자) |
| locks | 배열 | 풀이 잠금 달력(exam-data/locks.json 그대로). 항목은 { id, label, start, end } 예요(docs/시험_추가_방법.md 5장) |

형식 예시(sha256 자리는 설명으로 바꿔 적었어요):

```json
{
  "exams": [
    {
      "file": "files/exam-id.3.json",
      "id": "exam-id",
      "rev": 3,
      "sha256": "<files/exam-id.3.json 바이트의 SHA-256, 16진수 소문자 64자>"
    }
  ],
  "format": 1,
  "issuedAt": "2030-01-02T17:10",
  "locks": [],
  "seq": 2
}
```

실제 바이트는 테스트 전용 발행물 exam-data/testdata/test-only-valid/index.json 에서 볼 수 있어요(7장).

### 2-2. 글자 모양

- index.json 과 시험 파일은 모두 키를 정렬한 JSON 이에요(scripts/exams/canonical.ts): UTF-8(BOM 없음), 객체의 키는 UTF-16 코드 단위 순서(숫자 모양의 키도 글자로), 2칸 들여쓰기, 줄바꿈 LF, 끝에 줄바꿈 하나. 같은 값이면 늘 같은 바이트예요.
- 시험 파일은 앱의 시험 파일 검사(src/exams/validate.ts)를 통과한 시험 객체를 이 모양으로 적은 것이에요. 칸은 docs/시험_추가_방법.md 1장과 같아요. 원본 파일의 키 차례나 줄바꿈은 발행 파일에 남지 않아요.
- 같은 id 와 같은 rev 의 시험 파일은 늘 같은 바이트예요. 내용이 바뀌었는데 rev 가 그대로인 발행은 발행 도구가 거부해요(5장의 2번).
- 받는 쪽은 파일을 다시 직렬화하지 않고 받은 바이트 그대로 검사해요.

### 2-3. index.json.sig

- index.json 파일 바이트 그대로에 대한 Ed25519 서명(RFC 8032 의 Ed25519, 미리 해시하지 않는 방식) 64바이트를 표준 base64(패딩 포함, 88자)로 적은 한 줄과 LF 예요.
- 발행 도구는 node:crypto 의 sign(null, index.json 으로 쓰는 바이트, 비밀 키)로 서명하고, 서명한 바이트를 그대로 index.json 으로 써요.

### 2-4. 공개 키

- Ed25519 공개 키 32바이트(RFC 8032 의 인코딩, JWK 의 x 와 같은 바이트)를 표준 base64(패딩 포함, 44자)로 적은 한 줄과 LF 예요.
- 진짜 공개 키의 자리는 exam-data/public-key.txt 이고 커밋해요. 아직 없어요. 키를 맡은 사람이 `npm run exams:keygen` 으로 만들어요(비밀 키는 저장소 밖에만 둬요). 앱 껍데기에도 같은 공개 키를 넣어요(작업 지시서 4).
- 지문은 공개 키 32바이트의 SHA-256 을 16진수로 적은 것의 앞 16자예요. 비밀이 아니고, 발행 도구가 출력해요. 어느 키로 서명했고 어느 공개 키로 확인하는지 사람이 견줄 때 써요.
- 읽는 쪽은 끝의 줄바꿈 하나(LF 나 CRLF)만 빼고 base64 를 읽어요. exams:verify 는 줄바꿈이 없어도 받고, 그 밖의 빈칸, 두 줄 이상, PEM 은 받지 않아요. index.json.sig 도 같아요.

### 2-5. 시험 파일의 경로

발행 도구는 file 을 늘 files/<id>.<rev>.json 으로 적어요. exams:verify 는 아래 모양만 안전한 경로로 받고, 그 밖의 항목은 파일을 읽지도 받지도 않고 거부해요. 껍데기도 같은 규칙을 쓰면 돼요.

- / 로 나눈 조각마다 영어 글자, 숫자, 밑줄, 붙임표로 시작하고, 그 뒤에는 영어 글자, 숫자, 점, 밑줄, 붙임표만 와요(`^[A-Za-z0-9_-][A-Za-z0-9._-]*(?:/[A-Za-z0-9_-][A-Za-z0-9._-]*)*$`).
- 200자까지이고, index.json 과 index.json.sig 는 안 돼요.
- 그래서 '..', '.', 절대 경로, 역슬래시, 드라이브 글자(:), 퍼센트 인코딩(%), 쿼리(?), 숨은 파일, 빈 조각을 받지 않아요.

## 3. 받는 쪽 규칙(작업 지시서 3의 6-3)

아래 아홉 가지는 작업 지시서 3의 6-3을 그대로 옮겼어요. 작업 지시서 4(아이폰 껍데기)가 구현해요. 이 저장소에는 받는 쪽 코드가 없어요(웹은 스스로 통신하지 않아요).

1. index.json 과 index.json.sig 를 캐시를 쓰지 않고 받는다.
2. 앱에 든 공개 키로 서명을 확인한다. 실패하면 버리고 가지고 있던 자료를 그대로 쓴다.
3. format 이 아는 값이 아니면 버린다.
4. seq 가 가지고 있는 것보다 작으면 버린다(옛 자료로 되돌리는 것을 막는다). 같으면 그대로 둔다.
5. 시험 파일은 sha256 이 맞을 때만 받아들인다.
6. 모두 확인한 뒤에 한 번에 바꾼다. 도중에 하나라도 실패하면 가지고 있던 자료를 그대로 쓴다.
7. 받아들인 자료는 기기에 보관해서 통신이 없어도 쓴다.
8. 보내는 것은 없다. 요청에 기기나 사용자를 가리키는 값을 붙이지 않는다.
9. 기록이 가리키는 시험은 지우지 않는다.

발행한 쪽에서 같은 확인을 미리 하는 `npm run exams:verify`(scripts/exams/verify.ts)의 차례와 기준이에요. 껍데기도 이대로 하면 발행 도구가 통과시킨 발행물을 똑같이 받아들여요.

- 받기(1번, 8번): index.json 과 index.json.sig 를 받은 바이트 그대로 둬요. 주소로 받을 때는 캐시를 쓰지 않고(요청 머리글 Cache-Control: no-cache), 다른 주소로 넘기는 응답(3xx)을 따라가지 않고 실패로 봐요. 200 응답만 받아요. 쿼리, 쿠키, 계정, 기기 이름 같은 값을 붙이지 않아요. exams:verify 는 파일마다 15초를 기다려요.
- 서명(2번): index.json 받은 바이트 그대로에 대해 확인해요. 맞지 않으면 다른 것은 보지 않고 버려요.
- 목록(3번): 서명이 맞으면 index.json 을 엄격한 UTF-8 의 JSON 객체로 읽어요(BOM 이 있으면 읽지 못해요). format 이 1인지, seq 가 1 이상의 정수인지, issuedAt 이 실제로 있는 "YYYY-MM-DDTHH:mm" 인지, locks 가 잠금 달력 검사(src/exams/validate.ts 의 validateLocks)를 통과하는지, exams 의 항목마다 id(빈칸이 아니고 겹치지 않음), rev(1 이상의 정수), file(2-5의 안전한 경로, 겹치지 않음), sha256(16진수 소문자 64자)이 맞는지 봐요.
- 시험 파일(5번): 경로가 안전한 항목만 받아요. 받은 바이트의 SHA-256 이 index.json 의 sha256 과 같은지 보고, 그 바이트를 JSON 으로 읽어 시험 파일 검사(validateExam)를 통과하는지, 파일 안의 id 와 rev 가 목록과 같은지 봐요. 파일 하나는 5MB 까지 받아요. 크기는 다 받은 뒤가 아니라 받는 도중에 봐요: 길이 머리글(Content-Length)이 5MB 를 넘으면 본문을 받지 않고, 받는 동안 푼 바이트(전송 압축을 푼 뒤의 크기)의 합이 5MB 를 넘으면 그 자리에서 끊어요(index.json 과 index.json.sig 도 같아요).
- seq(4번): exams:verify 는 받는 쪽이 가진 seq 를 모르니 보지 않아요. 껍데기가 가진 자료의 seq 와 견줘요. 가진 자료가 없으면 seq 와 상관없이 받아요.
- 한 번에 바꾸기(6번)와 보관(7번): 위 확인을 모두 통과한 뒤에 한 번에 바꿔 보관해요. 새 발행물의 index.json 과 시험 파일로 바꾸되, 받아들인 적 있는 시험 가운데 새 발행물에 없는 것은 지우지 않고 마지막으로 받은 판을 남겨요(3-1 의 2번). 하나라도 받지 못하거나 틀리면 아무것도 바꾸지 않아요.
- 시험을 지우지 않음(9번): 발행 도구는 발행했던 시험 id 가 빠진 발행을 거부해요(5장의 1번). 다만 이 검사는 발행한 컴퓨터의 state.json 이 아는 시험만 봐서, 최신이 아닌 자료 폴더(다른 컴퓨터, git pull 을 빠뜨린 클론)로 발행하면 앞서 낸 시험이 빠진 발행물도 통과할 수 있어요(발행 쪽은 docs/시험_당일_순서.md 3-0 의 pull 과 주소 확인으로 막아요). 그래서 "정상 발행물에는 앞서 낸 시험이 늘 들어 있다"는 자료 폴더가 최신일 때만 맞아요. 웹은 기록이 가리키는 시험을 찾지 못해도 기록을 지우지 않고 "시험 자료를 받으면 다시 볼 수 있어요."를 보여 줘요. 껍데기가 지킬 것은 3-1 에 있어요.

### 3-1. 별도 검토에서 더한 받는 쪽 요구(작업 지시서 4로 넘김)

작업 지시서 3의 별도 검토(docs/화면검토기록.md 6장)에서 찾은 것 가운데 껍데기가 지켜야 하는 것이에요. 작업 지시서 4가 구현하고 시험해요.

1. 받는 도중의 크기 제한(별도 검토 C5): 3장의 시험 파일 항목대로 파일 하나 5MB 를 받는 도중에 지켜요. URLSession 의 data(from:) 처럼 다 받아 두는 방법을 쓰면 큰 응답이나 압축 폭탄으로 메모리를 크게 쓸 수 있어요. 길이 머리글이 5MB 를 넘으면 받지 않고, 받는 동안 푼 바이트의 합이 넘으면 끊고 그 발행물을 버려요(가진 자료를 그대로 써요).
2. 받아들인 시험은 id 로 남기기(별도 검토 C3): 새 발행물을 받아들일 때 보관한 시험을 통째로 바꾸지 않고 id 로 합쳐요. 받아들인 적 있는 시험 id 가 새 발행물에 없으면 그 시험의 마지막으로 받은 판을 지우지 않고 남겨 remote 의 exams 에 함께 넣어요. 최신이 아닌 자료 폴더로 낸 발행물이 와도 기록이 가리키는 시험이 사라지지 않게 하려는 것이에요(3장의 9번). 같은 id 의 시험은 rev 가 큰 판을 남겨요. 새 발행물의 판이 가진 판보다 작으면 가진 판을 그대로 둬요. 발행 도구로 낸 발행물에서는 같은 id 의 rev 가 내려가지 않아서, 더 작은 판은 최신이 아닌 자료 폴더로 낸 것이에요. 그런 판으로 바꾸면 정답 공개 전 판으로 돌아가 점수가 사라지거나, 정답 판 번호가 작은 예전 판이나 같은 정답 판 번호에 다른 정답이 든 판으로 점수 해부, 계단, 재풀이 기록이 알림 없이 바뀔 수 있어요(별도 검토 2차 Q1, Q2, Q4, Q6).
3. 배포용 빌드의 공개 키(별도 검토 C4): Release 빌드는 exam-data/public-key.txt 의 진짜 공개 키 하나만 믿어요. 테스트 전용 공개 키 두 개(exam-data/testdata 의 test-only-public-key.txt, 지문 f7e7dc5cfc6ce2a0 과, 서명이 틀린 발행물에만 쓴 다른 테스트 전용 키, 지문 99e0a1fa9d0331bc)가 Release 빌드에 들어 있으면 빌드가 실패해야 해요. 둘째 키는 파일로 두지 않았어요. scripts/exams/sign.ts 의 TEST_ONLY_KEY_NAMES 둘째 이름(score-anatomy/test-only-other-key/v1)의 SHA-256 을 Ed25519 씨앗으로 만든 키예요(별도 검토 2차 W12). 이 키들의 비밀 키는 저장소에 있어 누구나 서명할 수 있어요.
4. 시작할 때 보관한 자료를 바로 넘기기(별도 검토 D2): 껍데기는 보관한 자료가 있으면 시작할 때 `__SA_APP__` 의 remote 칸에 넣어요(4장). 시작한 뒤에 remote 알림으로 넘기면 그 사이 웹은 넘겨받은 시험의 기록을 "시험 자료를 받으면 다시 볼 수 있어요."로 보여 줘요.
5. 발행 도구는 앱 묶음에 든 시험(src/exams 의 예시 시험)과 같은 id 의 발행을 거부하고, 웹도 묶음 안 시험과 같은 id 인데 문항 구성(문항 수, no, kind, choices)이 다른 넘겨받은 판은 버려요(별도 검토 A2, B1, 4장). 껍데기는 받은 시험 id 를 바꾸거나 고르지 않고 3장의 확인을 통과한 그대로 넘겨요.

## 4. 다리 규격 2와의 관계

껍데기는 3장의 확인을 모두 통과한 자료만 웹에 넘겨요. 메시지와 웹이 하는 일은 docs/앱_다리_규격.md 7장에 있어요.

- 넘기는 모양: remote = `{ seq, issuedAt, exams, locks }` 예요. seq 와 issuedAt 은 index.json 의 값, exams 는 시험 파일을 JSON 으로 읽은 객체의 배열(index.json 의 exams 차례, 그 뒤에 3-1 의 2번대로 남긴 시험의 판), locks 는 index.json 의 locks 예요. store 와 달리 JSON 글자가 아니라 객체로 넣어요.
- 시작할 때: 보관한 자료가 있으면 `window.__SA_APP__` 의 remote 칸에 넣어요(bridge 가 2 이상일 때만 웹이 읽어요). 없으면 null 이에요.
- 켜져 있는 동안: 새 자료를 받아들이면(처음 받아들일 때도) 웹의 요청이 없어도 `window.__saFromApp({ type: "remote", remote })` 로 알려요. 시작할 때 remote 가 null 이었으면 웹은 받은 자료 안내와 "새로 확인" 버튼을 보여 주지 않다가, 이 알림을 받으면 보여 줘요.
- 새로 확인: 웹이 saRemote 로 `{ op: "refresh" }` 를 보내면 껍데기는 주소에서 다시 받아 3장대로 확인하고 remote 나 remoteFailed 를 하나 보내요. 새 자료가 없으면(seq 가 같거나 작음) 지금 가진 자료를 seq 그대로 remote 로 보내고(웹은 "이미 가장 새 자료예요."), 받지 못했거나 확인을 통과하지 못하면 `{ type: "remoteFailed" }` 를 보내요(웹은 "새 시험 자료를 받지 못했어요. 지금 있는 자료로 쓸 수 있어요.").
- 시간: 웹은 새로 확인의 응답을 10초 기다리고, 그동안 아무 응답이 없으면 받지 못한 것으로 다뤄요. 그 뒤에 온 remote 도 자료로는 받아요. 그래서 껍데기는 받기와 확인을 10초 안에 끝내는 것이 좋아요.
- 웹이 하는 일: remote 의 겉모양(seq 는 0 이상의 정수, issuedAt 모양, exams 와 locks 는 배열)을 보고, 시험을 하나씩 묶음 안 시험 파일과 같은 검사(src/exams/validate.ts 의 checkExam)에 다시 통과시켜요. 통과하지 못한 시험만 버리고 이유를 개발자 콘솔에 경고로 남겨요. 남은 시험은 묶음 안 시험과 id 로 합치고, 같은 id 는 rev 가 큰 쪽(같으면 넘겨받은 쪽)을 써요. 묶음 안 시험과 같은 id 인데 문항 구성이 다른 넘겨받은 판은 버리고, 고른 판의 answersRev 가 다른 판보다 작으면 경고를 남겨요(별도 검토 A2, B1). 잠금 달력은 묶음 안 달력과 id 로 합치고 같은 id 는 넘겨받은 항목을 써요. seq 가 지금 쓰는 자료보다 큰 remote 만 받아들여요(지금 쓰는 넘겨받은 자료가 없으면 seq 와 상관없이 받아요).
- 넘겨받은 자료는 기록(store.json)에 넣지 않아요. 받아들인 자료를 보관하고 다음에 켤 때 remote 로 다시 넣는 것은 껍데기 몫이에요(3장의 7번).
- 학생이 넣은 답과 표시는 넘겨받은 자료로 바뀌지 않아요. 정답이 정정된 판(answersRev 가 더 큰 판)을 받으면 웹이 지금 정답으로 다시 채점하고 정정 알림을 보여 줘요. answersRev 가 오르지 않았는데 점수가 채점한 때와 달라지면(같은 판 번호에 다른 정답, 예전 판) "채점한 때와 다른 시험 자료로 다시 채점했어요."를 알려요(별도 검토 B1).
- 묶음 파일의 manifest.json(ios/ScoreAnatomy/Web)에서 bridge 는 묶음이 돌아가는 가장 낮은 규격(1), bridgeMax 는 웹이 아는 가장 높은 규격(2)이에요. 껍데기는 자기 규격 번호가 그 사이면 묶음을 실을 수 있고, remote 를 넘기려면 `__SA_APP__.bridge` 를 2로 넣어요.

## 5. 발행 도구가 거부하는 변경

받는 쪽이 앞서 받은 자료를 믿고 쓸 수 있게, 발행 도구(exams:check, exams:publish)는 마지막 발행 기록(state.json)과 견줘 아래 변경을 거부해요(작업 지시서 3의 6-4).

1. 발행했던 시험 id 가 사라짐
2. 내용이 바뀌었는데 rev 가 그대로이거나, rev 가 내려감
3. answerReleased 가 true 에서 false 로 돌아감
4. 문항의 no, kind, choices 가 바뀜
5. 채점에 영향을 주는 값(answer, altAnswers, allCorrect, points)이 바뀌었는데 answersRev 를 올리지 않았거나 answersNote 가 없음
6. confirmed 가 true 인데 두 값이 다름
7. 잠금 달력 항목의 형식이 틀림

별도 검토(A2, B1) 뒤로 앱 묶음에 든 시험(저장소의 src/exams/*.json)과 같은 id 의 원본도 거부해요. 반대로 발행한 시험(state.json)과 같은 id 의 시험을 앱 묶음에 넣으면 `npm run build:app` 과 verify 11번이 묶음을 만들지 않고 멈춰요.

그래서 발행 도구로 낸 발행물에서는 같은 id 의 rev 가 내려가거나 문항 구성이 바뀌는 일이 없고, issuedAt 도 발행할수록 같거나 늦어요. 이 밖에 거부하는 것과 알리기만 하는 것은 docs/결정기록.md 6장에 있어요.

## 6. 고정 주소가 갖춰야 할 조건

주소는 아직 정하지 않았어요. 사람이 정하고, 정하면 껍데기(작업 지시서 4)에 넣고 이 장에 적어요. 앱은 이 주소 한 곳에서만 받아요. 앱에 들어가는 주소라서 오래 쓸 수 있는 주소여야 해요.

- https: 유효한 인증서가 있는 https 주소여야 해요. 아이폰 앱은 기본 설정에서 https 가 아닌 주소에 접속하지 않아요(App Transport Security).
- 정적 파일: index.json, index.json.sig, files 아래 시험 파일을 올린 바이트 그대로 내주는 곳이어야 해요. 줄바꿈이나 문자셋을 바꾸거나 JSON 을 줄이거나 다시 쓰면 서명과 SHA-256 이 맞지 않아 모든 기기가 그 발행물을 버려요(전송할 때 압축했다가 푸는 것은 괜찮아요). 서버 쪽 코드, 로그인, 쿠키, 쿼리 없이 GET 으로 열려야 하고, 다른 주소로 넘기지 않고 그 주소에서 바로 200 으로 내줘야 해요(받는 쪽은 넘기는 응답을 따라가지 않아요).
- 접속 기록을 되도록 남기지 않는 곳: 접속 기록(접속한 곳, 시각, 요청 머리글)을 남기지 않거나, 끌 수 있거나, 짧게 지우는 곳을 골라요. 분석 도구, 광고, 추적 스크립트, 쿠키를 붙이지 않는 곳이어야 해요. 학생 기기가 언제 자료를 받는지도 개인정보가 될 수 있어요.
- 캐시: index.json 과 index.json.sig 는 캐시하지 않거나 아주 짧게 두는 곳이어야 해요(Cache-Control: no-cache 나 no-store). 중간 캐시(CDN)를 쓰면 올린 뒤 바로 비울 수 있어야 해요. 늦게 바뀌면 학생이 옛 정답이나 옛 컷을 오래 봐요. 시험 파일은 이름에 rev 가 들어 있어 같은 이름이 다른 내용이 되지 않아요.
- 올리는 차례: files 폴더의 시험 파일을 먼저 올리고, index.json 과 index.json.sig 를 마지막에 함께 올려요. 둘 사이의 짧은 틈에 받은 기기는 서명이나 SHA-256 이 맞지 않아 그 자료를 버리고 가진 자료를 그대로 쓰니(3장의 2번, 6번) 다음에 다시 받으면 돼요. 그 전 발행의 시험 파일은 지우지 않고 남겨 둬도 돼요.
- 올린 뒤에는 `npm run exams:verify -- https://<정해진 주소>/` 로 주소에서 확인해요(docs/시험_당일_순서.md 5장).

## 7. 테스트 전용 발행물(exam-data/testdata)

- 작업 지시서 3의 6-5예요. 테스트 전용 키 쌍(test-only-private-key.pem, test-only-public-key.txt, 공개 키 지문 f7e7dc5cfc6ce2a0)으로 서명한 발행물 네 가지(test-only-valid, test-only-bad-signature, test-only-changed-byte, test-only-older-seq)예요. `npm run exams:testdata` 가 만들고 커밋했어요. 폴더마다 무엇이 다른지, 받는 쪽이 할 일, 받는 쪽 시험 순서는 exam-data/testdata/README.md 에 있어요.
- 이 키와 발행물은 진짜 발행에 절대 쓰지 않아요. 비밀 키를 저장소에 일부러 넣어 둬서 누구나 이 키로 서명할 수 있어요. exams:publish 는 이 키를 거부해요(저장소 밖으로 옮겨도 거부해요).
- 앱의 배포용 빌드(Release)에는 테스트 전용 공개 키를 넣지 않아요. 껍데기의 Debug 빌드나 테스트에서만 써요. Release 빌드에 테스트 전용 공개 키가 들어 있으면 빌드가 실패해야 해요(3-1 의 3번, 작업 지시서 4로 넘김).
- 시험 test-only-exam 과 날짜, 시각은 모두 테스트용으로 지은 형식 예시예요(isSample true, 제목 "테스트 전용 시험").
- `npm run verify` 의 13번이 네 폴더를 실제 Node 의 exams:verify 로 확인해요. 정상과 seq 가 작은 것은 통과하고(seq 비교는 받는 쪽 몫), 서명이 틀린 것과 시험 파일 한 바이트가 바뀐 것은 실패해요.

## 8. 발행 쪽에서 확인하는 명령

| 명령 | 하는 일 |
| --- | --- |
| `npm run exams:verify` | 발행 폴더(dist-exams)를 exam-data/public-key.txt 로 확인해요 |
| `npm run exams:verify -- <폴더>` | 다른 발행 폴더를 확인해요 |
| `npm run exams:verify -- https://<정해진 주소>/` | 올린 주소에서 받아 확인해요. 끝이 /index.json 인 주소도 받아요 |
| `npm run exams:verify -- <폴더나 주소> --key <공개 키 파일>` | 다른 공개 키로 확인해요(형식 예시: 테스트 전용 발행물은 `--key exam-data/testdata/test-only-public-key.txt`) |
| `npm run exams:serve` | 발행 폴더를 http://127.0.0.1:4180/ 에서 내줘요(리허설과 시뮬레이터 시험용, 이 컴퓨터에서만, TLS 없음). `--dir`, `--port` 로 바꿔요. 확인 안내는 기본이 아닌 발행 폴더면 발행할 때 쓴 자료 폴더를, 저장소의 테스트 전용 발행물이면 테스트 전용 공개 키를 붙여 적어요 |

- exams:verify 의 종료 코드는 0(맞음), 1(맞지 않거나 확인하지 못함), 2(인자가 틀림)예요. 결과는 맞으면 표준 출력, 틀리면 이유 목록을 표준 오류에 적어요.
- 폴더를 확인할 때는 목록에 없는 파일을 알리고, 자료 폴더의 마지막 발행(state.json)과 seq, issuedAt, 시험별 SHA-256, 잠금 달력이 다르거나 state.json 을 읽지 못하면 알려요(실패는 아님).
- 주소를 확인할 때(올린 뒤와 발행 전)는 자료 폴더의 마지막 발행과 다르거나 견주지 못하면 실패예요(종료 코드 1, 별도 검토 C2, 2차 T1, T4). 까닭은 넷으로 적어요. 주소의 것이 예전이면 새 발행물이 아직 다 올라가지 않았거나 캐시가 남은 것, 주소의 것이 더 새로우면 자료 폴더가 최신이 아닌 것(자료 폴더가 아직 발행한 적이 없는 seq 0 도 여기에 들어요. git pull 뒤 다시 확인하고 그 전에는 발행하지 않아요), seq 가 같은데 issuedAt, 시험, 잠금 달력 가운데 하나가 다르면 다른 자료 폴더에서 같은 seq 로 발행한 것, state.json 이 없거나 읽지 못하거나 모양이 틀리면 견주지 못한 것이에요. 공개 키가 테스트 전용이면 견주지 않아요(테스트 전용 발행물은 진짜 자료 폴더와 상관이 없어요, 2차 T2).

## 9. 형식을 바꿀 때

format 은 1이에요(scripts/exams/release.ts 의 RELEASE_FORMAT). 받는 쪽은 모르는 format 을 버리니(3장의 3번), format 을 올린 발행물은 그 format 을 모르는 앱이 모두 버리고 가진 자료를 그대로 써요. 형식을 바꾸는 일은 이 문서, 발행 도구, 껍데기를 함께 고치는 일이에요.

## 10. 확인하지 못한 것

- 실제 아이폰과 시뮬레이터에서 받기(작업 지시서 4).
- 아이폰의 CryptoKit 이 공개 키 32바이트와 서명 64바이트를 이 모양 그대로 받는지. Curve25519.Signing.PublicKey(rawRepresentation:) 로 읽는 모양으로 보이지만 해 보지 않았어요.
- 고정 주소의 호스팅이 바이트를 바꾸지 않는지, 캐시와 접속 기록 설정(주소를 정한 뒤 사람이 확인해요).
