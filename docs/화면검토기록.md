# 화면 검토 기록

결론: 화면 캡처(docs/screens)를 직접 열어 보고 어긋난 곳을 고쳤어요. 자동 검사가 잡은 것과 눈으로 찾은 것을 나눠 적어요. 만든 쪽이 아닌 별도 검토 단계가 찾은 것과 고친 내용은 4번에 있어요. 두 번째 검토 뒤에는 다시 찍은 캡처 192장(밝은 화면, 어두운 화면, 작은 화면 64장씩)을 모두 다시 열어 봤어요. 세 번째 검토 뒤에 카드 색과 글자 굵기를 고치고 다시 찍은 캡처는 밝은 화면 64장을 모두, 어두운 화면과 작은 화면은 32장씩 열어 봤고 어긋난 곳은 없었어요. 열어 보지 않은 캡처도 자동 화면 검사(겹침, 가려짐, 잘림, 간격)는 모두 거쳤어요.

## 1. 자동 검사가 잡아서 고친 것

화면 검사(e2e/audit.ts)를 처음 돌렸을 때 실패한 항목과 고친 내용이에요.

| 잡힌 문제 | 실제 수치 | 고친 내용 |
| --- | --- | --- |
| 바텀시트의 닫기 버튼과 바로 아래 버튼 사이 간격 | 2px (기준 8px) | 시트 머리와 본문에 여백을 더해 8px로 |
| 테스트 진행자용 화면의 답지 입력칸과 "답지와 비교하기" 버튼 사이 간격 | 4px (기준 8px) | 입력 칸 묶음 간격을 8px로 |
| 5행 방식 첫 쪽에서 진한 색 면적 | 10.7% (기준 10% 이하, 360x640) | "이전" 버튼을 첫 쪽에도 같은 자리에 두어 주 버튼 폭을 줄임 |
| 검사 코드 자체에 금지 문자가 들어 있음 | 2개 파일, 2곳 | 문자를 직접 적지 않고 코드 값으로 정규식을 만들게 바꿈 |

검사 방법 자체를 고친 것도 있어요.

- 화면이 바뀐 직후에 검사하면 이전 화면을 검사하는 일이 있었어요. 지금 그려진 화면의 주소를 html의 data-route 속성에 적고, 테스트가 그 값을 기다리게 했어요.
- 색이 바뀌는 전환(160ms) 도중에 색 대비를 재면 중간 색이 잡혔어요. 전환이 끝난 뒤에 재게 했어요.
- 스크롤 영역 안의 요소와 고정 영역의 요소 사이 간격은 스크롤 위치에 따라 달라져요. 간격은 같은 스크롤 영역 안에서 온전히 보이는 요소끼리만 재게 했어요.

## 2. 코드를 다시 읽고 계산해서 고친 것

자동 검사가 잡기 전에 디자인 기준과 견줘 보고 고친 것이에요. 수치는 색 값으로 계산한 값이에요.

| 문제 | 계산한 수치 | 고친 내용 |
| --- | --- | --- |
| 하단 탭 두 개의 터치 영역이 서로 붙게 됨 | 간격 0px (기준 8px) | 탭 사이에 8px 간격 |
| 진행 막대의 채운 부분과 바탕(장식용 경계선 색)의 대비 | 2.46:1 (기준 3:1) | 바탕을 배경색으로 바꾸고 윤곽색 테두리를 둠(3.38:1) |
| 5행 방식 번호 버튼의 테두리가 장식용 경계선 색 | 배경과 1.37:1 | 입력 테두리 색으로 바꿈(표면과 3.10:1) |

## 3. 캡처를 눈으로 보고 정한 것

| 본 것 | 판단 |
| --- | --- |
| 전화기 배열(세 칸 네 줄) 단답형 키패드가 화면 높이를 많이 차지함 | 숫자 두 줄 배열로 바꿈. 360x640에서 안내문이 떠도 한 화면에 들어옴 |
| 점수 해부 화면의 아래 고정 영역이 주 버튼, 글자 버튼, 탭으로 높음 | "입력 고치기"를 스크롤 영역 맨 아래로 옮겨 읽는 영역을 넓힘 |
| 키패드 방식 1~5번에서 직전 묶음 자리가 비어 보임 | 그대로 둠. 묶음이 넘어갈 때 칸 위치가 움직이지 않게 자리를 남겨 둔 것 |
| 표시 화면의 빗금 칸에서 글자 뒤에 배경색 띠가 보임 | 그대로 둠. 빗금 위에서도 글자 대비를 지키려고 글자 뒤만 배경색으로 칠함 |
| 계단 화면에서 긴 카드가 하단 탭 경계에서 잘려 보임 | 그대로 둠. 스크롤 영역의 경계 |
| 어두운 화면의 막대, 표식, 테두리 | 밝은 화면과 같은 무늬로 구분됨. 고칠 곳 없음 |

## 4. 별도 검토 단계가 찾은 것

검증은 만든 쪽이 아닌 별도 검토 단계가 맡았어요. 검토자는 모두 지시서의 관련 장 원문을 그대로 받았고, 코드를 고치지 않고 찾은 것만 보고했어요. 고치는 일은 만든 쪽이 했고, 고친 것마다 테스트를 더했어요.

### 4.1 첫 번째 검토: 지시서와 계산, 상태

| 찾은 것 | 고친 내용 |
| --- | --- |
| 테스트 진행 중에 참가자가 시험을 다시 고르면 측정 기록이 옛 기록에 묶인 채 끊어짐 | 이번 참가자가 만든 기록만 이어 쓰고, 측정 기록을 지금 기록에 다시 묶음 |
| 찍기 운 평균을 보기 수로 나눠 계산함(지시서는 0.2) | 지시서의 식 그대로 0.2 |
| 키패드 "지우기"가 지금 칸에 답이 있으면 지금 칸을 지움(지시서는 한 칸 뒤) | 늘 한 칸 뒤로 가서 지우고 무엇을 지웠는지 안내 |
| "없어요"가 표시를 붙이면 사라짐(지시서는 보조 버튼) | 늘 보이고, 누르면 표시 없이 채점 |
| 재풀이 라벨이 지시서의 조건과 다름(맞혔던 문항을 "정답 확인 후"로 적음) | 지시서의 조건 그대로. 이때 지시서에 없는 라벨 하나("N번째에 맞힘")를 더했는데, 4.3에서 지시서의 3종만 쓰게 되돌림 |
| 실수 행이 있는데도 "나눠 볼 것이 없어요"라고 적는 경우 | 원인을 표시했으면 "찍었다고 표시한 문항이 없어요"로만 적음 |
| 막대의 접근성 라벨에 값이 없는 구간을 "0점"이라고 읽음 | 값이 있는 구간만 읽음 |
| 등급컷 둘째 줄이 첫 줄 없이는 뜻이 통하지 않는 경우 | 첫 줄이 "남았어요"가 아니면 둘째 줄 끝을 "남았어요"로 적음 |
| 채점한 뒤 답을 고치면 점수가 말없이 바뀜 | 다시 채점하게 하고 "채점한 뒤에 답을 고친 문항"을 적음 |
| 다음 참가자에게 앞 사람의 기록이 "이어서 보기"로 열림 | 새 참가자를 시작하면 지금 보는 기록을 비움. 최종 답은 측정 기록에 따로 남김 |
| 저장된 값의 속이 망가져 있으면 흰 화면이 됨 | 모양이 맞는 값만 읽고, 그래도 오류가 나면 돌아갈 길을 보여 줌 |
| 마지막 단답형을 "전체 보기"로 넘기면 입력 완료 시각이 안 남음 | 입력 확인 화면에 들어올 때 다 차 있으면 그때를 완료 시각으로 |
| 테스트 진행자용 화면의 주 버튼이 스크롤 영역 안에 있음 | 아래 고정 영역으로 옮김 |
| 13px 글자와 배지의 굵기, 키패드 좌우 여백이 디자인 기준과 다름 | 굵기 400, 좌우 여백 20px |
| 결과 화면 몇 곳에 "예시" 배지가 없음 | 예시 시험이면 점수, 오답 원인, 계단, 재풀이 화면에도 "예시" 배지 |
| 쓰지 않는 문구가 문구 파일에 남아 있음 | 지움 |

### 4.2 두 번째 검토: 화면 조작과 검증 코드

| 찾은 것 | 고친 내용 |
| --- | --- |
| 같은 자리를 두 번 누르면 다음 화면의 버튼까지 눌림(마지막 답을 넣자마자 탭이 눌리는 경우 등) | 화면과 바텀시트가 나타난 뒤 0.5초 동안 아래 고정 영역이 누름을 받지 않음. 이 방식의 부작용을 4.3에서 찾아 다시 바꿈 |
| 단답형 숫자가 "다음"을 누르기 전에 저장됨 | 누르고 있는 숫자는 따로 들고 있다가 "다음"에서만 저장 |
| 글자를 키우거나 화면이 낮으면 키패드 화면의 칸과 안내문이 잘림 | 위쪽이 스크롤되고, 안내문은 키패드 바로 위에, 지금 칸으로 자동 이동 |
| 한글 낱말 가운데에서 줄이 바뀜 | 낱말 단위로 줄바꿈 |
| 입력 확인 바텀시트에서 지금 답이 테두리 색으로만 구분됨 | "지금 답" 글자를 함께 적음 |
| 입력 확인과 표시 화면에 하단 탭이 없음 | 탭을 보여 줌(답 입력 화면에서만 숨김) |
| 점수가 높으면 막대 아래 눈금 숫자 둘이 겹침 | 두 줄로 나눠 적음 |
| 기록을 지운 뒤 뒤로 가면 다른 시험의 결과가 열림 | 지금 보던 기록을 지우면 지금 보는 기록 없음 상태로 |
| 폭 320px에서 5행 방식의 다섯째 보기가 화면 밖으로 나감 | 지원 범위보다 좁은 폭에서는 간격과 터치 영역을 줄임 |

검증 코드에서 찾은 빈틈과 고친 내용이에요.

| 빈틈 | 고친 내용 |
| --- | --- |
| 가려짐을 요소 가운데 한 점으로만 봄 | 가운데와 네 귀퉁이 다섯 점 |
| 상자에 잘린 글자, 칼럼 밖으로 나간 요소를 못 잡음 | 잘림 검사를 더함 |
| 입력 칸 글자 16px를 검사하지 않음 | 검사를 더함 |
| 금지 문자 검사가 접힌 글자, 입력 칸 값, 가상 요소 글자를 안 봄 | 모두 봄 |
| 색 대비를 색 값 계산으로만 봄 | 그려진 글자와 테두리를 투명도까지 넣어 다시 잼 |
| 주 숫자와 주 버튼 개수를 클래스 이름으로 셈 | 계산된 글자 크기와 칠한 색으로 셈 |
| 정답색과 오답색을 넓은 면에 썼는지 안 봄 | 검사를 더함 |
| 외부 요청을 탭 하나에서만 셈 | 브라우저 묶음 전체(새 창, 워커 포함)에서 셈 |
| 정답 노출 검사가 정답 숫자를 찾는 방식뿐임 | 정답만 다른 두 빌드의 화면을 통째로 견주는 검사를 더함 |
| 화면 캡처 코스에 만점, 컷 범위 안, 낮은 점수, 컷 자료 없음 상태가 없음 | 상태를 더해 64장으로 |
| "좌표 복사"가 안내문만 확인함 | 클립보드에 들어간 글자까지 확인 |

### 4.3 세 번째 검토: 관점 4개와 반박 검증

검토자 4명이 관점을 나눠 따로 봤어요(계산과 상태, 화면과 흐름, 디자인과 기술 조건, 검증과 문서). 찾은 것마다 다른 검토자가 반박을 시도했어요. 찾은 것은 35건이고, 반박 검증에서 32건이 확인되고 3건이 반박됐어요. 여러 검토자가 같은 것을 찾은 경우는 아래에서 한 줄로 묶었어요.

| 찾은 것 | 고친 내용 |
| --- | --- |
| 화면이나 바텀시트가 뜬 직후 0.5초 동안 누른 키가 말없이 버려져, 누른 것과 다른 답이 저장됨(150이 50으로, 키패드 방식에서는 답이 한 칸씩 밀림, 재풀이는 틀린 기록으로 남음) | 영역 전체를 막지 않고 바로 앞에 누른 자리만 막게 바꿈(src/tapGuard.ts). 다른 자리의 키는 바로 들어감 |
| 바텀시트나 삭제 확인이 닫힌 직후, 아래 버튼이 바뀐 직후에 같은 자리를 다시 누르면 밑의 버튼이 눌림(입력 확인에서 표시 화면으로 넘어감, 기록 화면으로 나감, 5행 방식의 쪽이 넘어감, 정답 공개 전 안내문을 건너뜀, 다른 기록이 열림) | 층이 닫힐 때, 아래 버튼이 바뀔 때, 쪽이 넘어갈 때도 같은 자리를 막음. 두 경우를 테스트 9개로 남겼고, 고치기 전 빌드에서는 9개가 모두 실패하는 것을 확인함 |
| 참가자를 마친 뒤 그 시험 기록을 고치면 끝난 측정의 최종 답과 남은 오입력, 내보낸 값이 따라 바뀜 | 끝난 측정은 마칠 때 옮겨 둔 사본만 쓰고, 사본을 다시 덮어쓰지 않음 |
| 시험 기록을 지운 뒤에는 답지 대조가 막히고 "넣은 답이 아직 없어요"라고 나옴 | 옮겨 둔 최종 답이 있으면 대조함 |
| 앞 기록의 점수 화면을 먼저 열면 "시험 선택부터 첫 점수까지"가 음수로 나옴 | 측정에 묶이지 않은 기록의 화면은 other: 를 붙여 따로 적고 시각 측정에 쓰지 않음 |
| 답을 넣다가 다른 시험으로 바꾸면 앞 시험에서 누른 횟수가 새 시험의 측정에 섞임 | 입력 측정을 비우고 다시 고른 횟수를 측정 카드와 CSV에 적음 |
| 다시 풀다 틀린 뒤에 맞히면 지시서에 없는 라벨 "N번째에 맞힘"이 나오고 같은 카드의 문장과 어긋남 | 지시서의 3종만 씀. 다른 라벨은 제안 12번으로 옮김 |
| "이미 했어요"를 고른 뒤 "아직 안 했어요"로 다시 골라도 기록이 바뀌지 않음 | 방금 고른 답으로 바꿈 |
| 지금 보던 기록을 지우면 다른 기록이 남아 있어도 "이어서 보기"가 없음 | 남은 기록 가운데 가장 최근 것을 열게 함. 테스트 중에는 이번 참가자의 기록만 |
| 단답형에서 숫자를 다 지우고 "다음"이나 "넣기"를 눌러도 저장된 답은 남아서 "비어 있어요" 안내문이 사실과 다름 | 다 지운 채 "다음"이나 "넣기"를 누르면 그때 저장된 답을 지움. 누르기 전에는 답이 그대로 |
| 확정하지 않은 숫자가 "전체 보기"와 위쪽 뒤로 가기에서 말없이 사라짐 | 버린 숫자를 알리고 한 번 머묾. 다시 누르면 나감 |

### 4.4 네 번째 검토: 고친 것을 다시 확인

세 번째 검토 뒤에 고친 것을 검토자 4명이 관점을 나눠 지시서 원문과 다시 대조했고(누르기 보호와 답 입력, 측정 기록과 상태, 디자인과 접근성과 문구, 검증과 문서와 산출물), 다섯 번째 검토자가 빠진 곳을 골라 점검했어요. 찾은 것은 25건이고(중간 5건, 낮음 20건) 같은 것을 묶으면 21건이에요. 이번에는 반박 단계를 따로 두지 않았어요. 찾은 것마다 만든 쪽이 다시 재현해 보고 고친 뒤 테스트로 남겼어요.

점검자가 문제로 올리지 않고 참고로만 적은 것도 하나 고쳤어요. 키패드 방식에서 마지막 문항을 넣은 뒤 같은 박자로 더 누르면, 넘어간 화면의 다른 자리에 있는 "맞아요, 다음으로"와 "없어요"가 차례로 눌려 입력 확인과 표시를 건너뛴 채 채점됐어요. 마지막 문항을 넣어 저절로 넘어간 직후 0.5초는 화면 전체가 누름을 받지 않게 했어요(결정 기록 6번).
