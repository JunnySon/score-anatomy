# iOS 앱 껍데기 검토 기록

결론: 구현에 참여하지 않은 에이전트 네 명이 서로 다른 관점(다리 규격, 기록을 잃는 경로, 원칙, 검증의 빈틈)으로 코드를 읽어 26건을 찾았어요. 찾은 것마다 다른 에이전트 둘이 따로 반박을 시도했고(하나는 코드 경로를 끝까지 따라가 반박, 하나는 사용자와 지시서에 대한 영향 판단), 둘 다 맞다고 본 11건은 모두 고쳤어요. 한쪽만 맞다고 본 6건 가운데 5건은 고치거나 보강했고 1건은 이미 다른 곳에서 막혀 있어 그대로 뒀어요. 둘 다 아니라고 본 9건 가운데 3건은 비용이 작아 보강했어요. 껍데기 코드 자체(저장, 보관, 다리, 차단)에서 기록을 잃거나 규격을 어기는 결함은 나오지 않았고, 찾은 것은 대부분 검증 도구(verify.sh, verify_report.py)와 테스트의 빈틈이었어요.

- 검토한 날: 2026-11-24
- 검토한 코드: ios-v1 브랜치의 커밋 c37db04(껍데기, 단위 테스트, 화면 테스트, verify.sh, verify_report.py)
- 방법: 읽기만 하는 검토(파일을 고치지 않음). 검토자 4명, 반박 검증자 52명(찾은 것마다 2명). 판정은 두 검증자가 모두 맞다고 하면 "확인", 하나만 맞다고 하면 "가능성", 둘 다 아니라고 하면 "기각".
- 검토와 별도로 내가 개발 중에 찾아 고친 것(웹뷰 생성 시점, libswiftWebKit, XCTest 가 멈추는 문제)은 docs/ios_결정기록.md 에 있어요.

## 2. 가능성(한쪽만 맞다고 본 것, 6건)

| 번호 | 관점 | 찾은 것 | 처리 |
| --- | --- | --- | --- |
| 가능성 1 | 원칙 | 프로젝트 동기화 결과를 판정에 쓰지 않음 | 확인 9 와 함께 고침 |
| 가능성 2 | 원칙 | 6번 판정이 매니페스트 내용, 사유 API 기호, Info.plist 값을 보지 않음 | 확인 6, 10 과 함께 고침 |
| 가능성 3 | 검증 | 탐침의 window.open 과 스크립트 click 은 WebKit 의 팝업 차단이 먼저 막아서 껍데기의 새 창 처리(createWebViewWith)에 닿지 않아요. window.open 이 null 인 것은 껍데기를 증명하지 않아요 | 보강. 탐침 뒤에 새 창 링크와 바깥 링크를 페이지에 붙이고 XCUITest 로 실제로 눌러요(사람의 동작이라 팝업 차단을 지나요). 껍데기가 새 창을 막고(blockedWindows) 바깥 이동을 취소했는지(blockedNavigations), 요청 내용이 0인지 확인해요. 이때 링크 이동에서 WebKit 이 내용 없는 TCP 연결을 미리 맺는 것을 찾아, 하위 자원과 이동을 나눠 세도록 바꿨어요(docs/ios_결정기록.md) |
| 가능성 4 | 검증 | 진행자용 화면의 키보드와 글 입력, 튕김, 길게 누름 미리보기, 가장자리 밀기를 확인하는 테스트가 없음 | 보강. 화면 테스트 KeyboardInputTests(진행자용 화면의 참가자 코드 칸을 눌러 자판으로 P01 을 넣고 값과 초점, 칸이 자판에 가리지 않는지 확인)와 단위 테스트 ShellConfigurationTests(튕김, 미리보기, 가장자리 밀기, 비지속 웹 저장소, 팝업, 사기 사이트 경고, 자동 링크, 웹 검사기)를 더했어요 |
| 가능성 5 | 검증 | Release 구성을 한 번도 켜 보지 않음 | 보강. verify.sh 가 Release 구성으로 테스트 빌드를 만들어 ReleaseSmokeTests 를 돌려요. 시작 화면과 앱 안 문구가 뜨고, 기록 화면에 진행자용 링크와 "준비 중인 기능"이 없고, DEBUG 실행 인자(기록 위치, 기록 심기, 탐침, 불러오기 실패)가 아무 일도 하지 않는지 봐요(14번 판정) |
| 가능성 6 | 검증 | 소스 검사 결과가 없으면 6번 정적 검사가 0건으로 통과함 | 고침. 검사 결과가 없으면 6번과 11번이 실패가 돼요 |

## 4. 검토 뒤 더 알아본 것: 표시 화면의 두 번 누름

기각 7 을 살피다가, XCUITest 의 doubleTap(손을 떼고 약 2ms 만에 다시 누름)으로 표시 칸을 누르면 "찍음"이 아니라 "고민"에 그치는 것을 봤어요. 웹에 오는 이벤트를 기록해 보니 이랬어요.

- 따로 누른 한 번: 손을 뗀 뒤 약 2ms 에 click(detail 1)이 와요.
- 약 0.4초 간격으로 두 번: click(detail 1), click(detail 2), dblclick 이 와서 두 번 모두 들어가고 "찍음"이 돼요.
- 손을 떼고 2ms 만에 다시 누름: 첫 click 이 오기 전에 둘째 누름이 시작돼서, WebKit 이 click 하나(detail 2)와 dblclick 만 내요. 한 번만 들어가 "고민"이 돼요.

사람의 두 번 누름(0.2초 안팎)은 손을 떼고 다시 누르기까지 보통 0.1초쯤 걸려서 첫 click(2ms)보다 훨씬 늦으므로 두 번 모두 들어간다고 봐요. 다만 XCUITest 로 0.2초 간격을 그대로 낼 수 없어서 확인하지 못했어요. 실기기 확인표 5번에서 사람이 확인하고, 웹 쪽에는 표시 칸에서 dblclick 을 받으면 찍음까지 가게 하는 방법을 제안으로 적었어요(웹 파일은 고치지 않았어요).
