## 2. 내가 정한 것

### 기술

1. 버전: 작업한 날의 최신 안정 버전을 썼어요(Vite 8, React 19, TypeScript 7, Vitest 5). Playwright는 작업 환경에 설치돼 있던 Chromium과 맞는 1.63.0으로 고정했어요. 이유: 지시서가 버전을 정하지 않았고, 브라우저를 새로 내려받지 않고도 검증이 돌게 하려고요.
2. 라우터와 단일 HTML 빌드는 라이브러리 없이 직접 만들었어요(src/router.ts, scripts/inline-single.mjs). 이유: 화면이 12개뿐이고, 의존성이 적을수록 외부 요청 0건과 파일 하나 빌드를 보장하기 쉬워서요.
3. 화면이 어디인지는 앱이 기억하는 값이 기준이고 주소의 # 뒤는 그 값을 따라가요. 주소를 바꿀 수 없는 환경에서는 주소를 건드리지 않고 화면만 옮겨요. 이유: 아티팩트 뷰어처럼 주소 해시를 마음대로 쓸 수 없는 곳에서도 열리게 하려고요.
4. 저장: localStorage의 키는 score-anatomy 하나, version은 1이에요. 버전이 다르거나 통째로 읽을 수 없으면 처음 상태로 열어요. 일부만 망가져 있으면 모양이 맞는 값만 남기고 읽어요. 그래도 화면을 그리다 오류가 나면 흰 화면 대신 "화면을 그리지 못했어요."와 처음 화면으로 가는 링크를 보여 줘요. 이유: 시제품이라 옛 형식을 옮기는 코드를 미리 만들 근거가 없고, 저장된 값 때문에 앱이 안 열리는 일은 막아야 해서요. 1.1에서 더한 칸(기록의 selfChecks, 측정 기록의 discardedTaps)은 없어도 빈 값으로 읽어요. 저장 형식의 version 은 1 그대로예요(올리면 저장된 기록이 처음 상태로 열려요).
5. 바텀시트와 삭제 확인 대화상자가 열려 있는 동안 뒤 화면은 inert 속성으로 막아요. 이유: 뒤에 있는 키패드나 버튼이 눌리지 않게 하려고요.
6. 연달아 누르기 보호: 화면이 바뀌면 그 화면을 바꾼 누름의 자리(가로세로 48px)에 다시 온 누름을 0.5초 동안 받지 않아요. 받지 않은 누름이 있으면 그때부터 0.5초를 다시 세고, 다른 자리를 누르면 바로 풀어요(src/tapGuard.ts). "화면이 바뀜"은 다른 화면으로 넘어감, 바텀시트나 대화상자가 열리거나 닫힘, 아래 버튼이 다른 버튼이 됨, 5행 방식의 쪽이 넘어감, 키패드 방식에서 칸을 눌러 묶음이 바뀜, 키패드가 5지선다용과 단답형용 사이에서 바뀜, 시험 선택에서 고른 뒤 화면이 저절로 스크롤됨을 말해요. 화면을 요소로 가리지 않고 그 자리에 온 누름(click)만 버려서, 같은 자리에서 시작한 스크롤은 그대로 돼요. 단답형 숫자 키는 버리지 않아요. 숫자는 "다음"이나 "넣기"로 확정하기 전에는 저장되지 않고 큰 칸에 보이지만, 숫자를 버리면 누른 것과 다른 답(150 대신 50)이 저장될 수 있어서예요. 이유: 별도 검토에서 같은 자리를 두 번 누르면 다음 화면의 버튼까지 눌리는 것을 찾았어요. 처음에는 아래 고정 영역과 바텀시트 전체를 0.5초 막았는데, 세 번째 검토에서 그 방식이 화면이 바뀐 직후에 누른 다른 키까지 말없이 버리는 것을 찾아 "같은 자리"만 막게 바꿨어요. 그때는 보이지 않는 요소로 그 자리를 가렸는데, 네 번째 검토에서 그 요소가 스크롤까지 막고 숫자 키를 버리는 경우가 남는 것을 찾아 지금 방식으로 바꿨어요. 화면 전체를 막는 곳은 한 군데예요. 키패드 방식에서 마지막 문항의 답을 넣어 저절로 입력 확인으로 넘어간 직후 0.5초예요(받지 않은 누름이 있으면 다시 세요). 이유: 네 번째 검토의 빠진 것 점검에서, 마지막 문항 뒤에 답을 넣던 박자로 더 누르면 다른 자리에 있는 입력 확인의 "맞아요, 다음으로", 표시의 "없어요"가 차례로 눌려 확인과 표시를 건너뛴 채 채점되는 것을 찾았어요. 이 화면 전환만 답 키가 일으키고, 넘어간 화면에서는 버려진 누름이 답을 바꾸지 않아요. 남는 한계: 화면이 바뀐 직후 0.5초 안에 같은 자리에 온 5지선다 답 키나 버튼을 누르면 그 누름은 버려져요(예: "답 넣기"를 누른 자리에 온 1번 문항의 답 키). 거꾸로 숫자 키는 버리지 않아서, 줄이나 칸을 연달아 누르면 그 자리에 온 숫자가 큰 칸에 한 자리 들어갈 수 있어요(확정하기 전이라 저장되지는 않아요). 그 밖의 화면 전환(버튼을 눌러 넘어간 경우)에서는 다른 자리를 바로 누르면 새 화면의 버튼이 눌려요. 1.1부터 버린 누름이 누를 수 있는 요소 위였으면 "화면이 막 바뀌어서 방금 누른 것은 받지 않았어요."를 띄우고(83번), 측정 중이면 버린 누름을 세요(82번). 보호의 시간, 거리, 대상은 바꾸지 않았어요.
7. 한글 문장은 단어 가운데에서 줄이 바뀌지 않게 했어요(word-break: keep-all). 칸보다 긴 낱말만 가운데에서 바뀌어요.

### 데이터

### 계산

14. 찍기 운을 평균으로 본 점수는 찍음 표시 문항마다 1 나누기 보기 수(choices, 없으면 5)를 맞힐 확률로 보고 정수로 계산해요(1.1, 작업 지시서 1의 3-5). G는 실제 점수에서 추측 표시 정답 점수를 뺀 값, D는 찍음 표시 문항들의 보기 수의 최소공배수, N은 찍음 표시 문항마다 배점 x (D / 보기 수)를 더한 값이고, 값은 (G x D + N) / D 예요. 화면의 "약 N점"은 (2 x (G x D + N) + D)를 (2 x D)로 나눈 몫이라 딱 0.5는 올라가요. 찍음 표시가 없으면 D = 1, N = 0 이에요. 등급컷 상자 둘째 줄의 남은 점수는 화면에 보이는 반올림 값으로 계산해요. 이유: 보기가 5개가 아닌 시험이 들어오면 0.2가 맞지 않고, 소수 계산은 딱 0.5 같은 경계에서 어긋날 수 있어요. 이번에는 계산만 보기 수를 따르고, 보기 수가 5가 아닌 시험의 화면 지원은 범위 밖이에요. 1.0에서는 지시서의 식 그대로 0.2를 썼어요.
15. 계단에서 점수가 같을 때의 "문항 번호가 앞선 유형"은 그 유형에서 점수에 들어간 문항(틀린 문항과 찍음 표시 정답) 가운데 가장 앞선 번호로 견줘요.
16. 계단 카드의 배점 문장은 유형 이름 아래 줄에 두고(줄바꿈 허용) 틀린 문항 배점과 찍음 표시 정답 배점을 있는 것만 함께 적어요(1.1, 작업 지시서 1의 3-1). 둘 다 있으면 "놓친 배점 8점, 찍었다고 표시한 정답 4점", 틀린 문항만 있으면 "놓친 배점 8점", 찍음 표시 정답만 있으면 "찍었다고 표시한 정답 3점"이에요. 검산 예시는 적분, 수열, 확률 순으로 "놓친 배점 8점, 찍었다고 표시한 정답 4점", "놓친 배점 8점", "놓친 배점 3점, 찍었다고 표시한 정답 3점"이에요. 이유: 1.0에서는 틀린 문항 배점만 적어서 카드 숫자가 8점, 8점, 3점으로 보였고, 카드만 봐서는 순서(12, 8, 6)가 읽히지 않았어요.
17. 안 푼 문항에 붙은 표시는 계산에 쓰지 않아요. 답을 안 풂으로 바꾸거나 지우면 그 문항의 표시도 지워요. 이유: 고르지 않은 문항을 "찍음"으로 계산하면 추정 점수가 달라져 버려요.
18. 범위를 벗어난 값(저장소가 망가진 경우)은 미입력으로 봐요. 이유: 몰래 오답 처리하지 않으려고요.

### 답 입력

19. 키패드 방식의 "지우기"는 눈에 보이는 지금 칸부터 지워요(1.1, 작업 지시서 1의 3-3). 단답형은 큰 칸에 숫자가 보이면(방금 누른 숫자든 불러온 답이든) 한 자리씩 지우고 저장된 답은 그대로예요. 큰 칸이 빈 상태에서 한 번 더 누르면 지금 칸에 저장된 답을 지우고 머물러요. 안 풂은 한 번에 지워요. 5지선다는 지금 칸에 답이나 안 풂이 있으면 지우고 머물러요. 지금 칸이 빈칸이면, 이어서 들어온 칸일 때만 앞 번호로 가서 그 답을 지우고(방금 넣은 답을 바로 지우는 길이에요), 빈칸을 눌러 들어왔거나 고치기로 들어왔으면 다른 문항을 지우지 않고 "지울 답이 없어요."를 보여 줘요. 지웠을 때는 "N번 답을 지웠어요."라고 알려요. 숫자를 다 지운 채 "다음"(바텀시트는 "넣기")을 누르면 그때 들어 있던 답을 지우고 "N번이 비어 있어요..."라고 알려요(73번). 키패드가 잠겨 있을 때의 "지우기"는 72번(답을 넣어 잠긴 때)과 87번(빈칸 없이 연 때)이에요. 이유: 1.0에서는 지시서대로 늘 한 칸 뒤로 가서 지워서, 칸을 눌러 간 문항에서 누르면 눈에 보이는 큰 번호가 아니라 그 앞 문항이 지워졌어요.
20. 단답형에서 누른 숫자는 "다음"을 눌러야 답으로 들어가요. 숫자를 누르다 말고 다른 칸을 누르면 그 숫자는 버리고 "N번에 누른 숫자는 '다음'을 누르지 않아서 들어가지 않았어요."라고 알려요. "전체 보기"나 위쪽 뒤로 가기를 눌렀을 때도 같은 안내문을 보여 주고 그 화면에 한 번 머물러요. 다시 누르면 나가요. 이유: 지시서의 "다음을 눌러야 확정"을 그대로 지키고, 확정하지 않은 숫자가 몰래 저장되거나 말없이 사라지지 않게 하려고요. 브라우저의 뒤로 가기는 앱이 막지 못해서 이때는 안내 없이 버려져요.
21. 단답형 키패드는 숫자를 두 줄(1~5, 6~0)로 놓고 그 아래에 "안 풂", "지우기", "다음"을 뒀어요. 이유: 전화기 배열(세 칸 네 줄)로 먼저 만들어 390x844 캡처에서 재 보니 키패드가 297px을 차지했어요. 같은 배치를 높이 640px에 넣으면 남는 높이가 0px 안팎이라 안내문이 들어갈 자리가 없다고 계산했어요. 폰 브라우저는 주소 줄 때문에 실제 높이가 640px 안팎인 경우가 많아요. 두 줄 배열은 5지선다 키패드와 틀(가로 다섯 칸, 그 아래 기능 키 한 줄)이 같아서 "같은 틀"이라는 지시에도 맞아요. 다만 숫자가 두 줄이라 1~5 줄은 5지선다 때보다 한 줄 위에 놓이고, 5지선다의 1~5 자리에는 6~0 줄이 와요.
22. 안내문("답은 0부터 999까지예요." 등)은 키패드 바로 위에 띄워요. 글자를 키웠거나 화면이 낮아서 내용이 넘치면 위쪽이 스크롤되고, 지금 넣을 칸이 보이게 자동으로 옮겨요. 이유: 별도 검토에서 글자 크기 20px 이상이나 높이 560px에서 안내문과 칸이 잘리는 것을 찾았어요. 1.1부터 같은 자리에 키패드 잠금과 고치기 안내, 그리고 "M번도 고치기", "K번부터 이어서 넣기" 버튼을 띄워요(작업 지시서 1의 3-2). 안내문이 떠 있는 동안에는 본문의 안내 한 줄이 자리를 내줘요.
23. 5행 방식은 폭 360px에서 좌우 여백을 16px로 줄였어요(지시서는 20px). 이유: 번호 버튼 1개와 원 5개에 48px 터치 영역과 8px 간격을 주면 328px이 필요해요. 폭 368px 이상에서는 20px이에요. 지원 범위보다 좁은 폭(360px 미만)에서는 화면 밖으로 나가지 않게 간격과 터치 영역을 줄여요.
24. 5행 방식의 "이전" 버튼은 첫 쪽에서도 같은 자리에 누를 수 없는 상태로 둬요. 이유: 버튼 자리가 쪽마다 달라지지 않게 하고, 주 버튼이 화면 폭을 다 차지하면 고른 원 5개와 합쳐 진한 색 면적이 10%를 넘었어요(360x640에서 10.7%).
25. 5행 방식의 마지막 쪽 주 버튼은 "넣은 답 확인하기"예요. 단답형 줄의 숫자 키패드는 바텀시트로 열고 "넣기"로 확정해요. 닫으면 바뀌지 않아요. 시트의 "지우기"는 누르고 있는 숫자만 지우고 저장된 답은 건드리지 않아요(입력 확인의 단답형 시트도 같아요). 처음에는 빈 칸에서 "지우기"를 한 번 더 누르면 저장된 답이 안내 없이 지워졌는데, 세 번째 검토 뒤에 고쳤어요.
26. 입력 확인의 5지선다 바텀시트에서는 지금 들어 있는 답의 키에 "지금 답"이라는 글자를 함께 적어요. 이유: 테두리 색만으로 구분하지 않으려고요.

### 표시, 채점, 오답 원인

27. 표시 화면의 채점 버튼은 하나예요(1.1, 작업 지시서 1의 3-4). 표시가 하나도 없으면 "없어요, 채점하기", 하나라도 있으면 "채점하기"이고 자리와 크기는 같아요. 누르면 지금 붙어 있는 표시 그대로 채점하고 표시를 지우지 않아요. 라벨이 바뀌는 것은 연달아 누르기 보호 대상에 넣지 않아요(같은 칸을 빠르게 두 번 눌러 붙이는 "찍음"의 둘째 누름이 버려지지 않게). 정답 공개 전 시험의 "답 저장하기"는 그대로예요. 이유: 1.0에서는 "없어요"와 "채점하기"가 나란히 있었고, 표시를 붙인 뒤 "없어요"를 누르면 붙인 표시가 말없이 지워졌어요.
28. 앱에서 채점한 뒤에 표시를 바꾸면 "이미 했어요" 경로와 똑같이 "채점한 뒤에 표시한 기록이에요"를 적어요. 이유: 결과를 본 뒤의 표시를 채점 전 표시처럼 보이게 하지 않으려고요.
29. 채점한 뒤에 답을 고치면 점수 화면으로 바로 가지 않고 표시 화면에서 다시 채점하게 해요. 다시 채점한 결과 화면에는 "채점한 뒤에 답을 고친 문항: N번"을 작게 적어요. 고친 문항의 원인과 재풀이 기록은 지워요. 이유: 점수가 말없이 바뀌지 않게 하고, 결과를 본 뒤에 고친 답이라는 사실을 남기려고요.
30. 정답 공개 전 시험의 주 버튼은 "답 저장하기"예요. 저장한 뒤 안내문과 "기록 보기"가 나와요. 이유: 채점이 일어나지 않는데 "채점하기"라고 쓸 수 없어서요.
31. "건너뛰기"는 원인을 고르지 않은 문항이 남아 있을 때만 보여요.
32. 입력 확인과 표시 화면에도 하단 탭을 보여요. 답 입력 화면에서만 탭을 숨겨요.

### 점수 해부, 계단, 재풀이

33. 100점 막대와 표식은 포인트색이 아니라 그래프 윤곽색 한 가지로 그리고 무늬로만 갈랐어요. 포인트색은 누를 수 있는 것과 고른 것에만 써요. 이유: 360x640 화면에서 주 버튼 하나가 계산으로 화면의 7.2%(320x52px)예요. 막대까지 포인트색으로 칠하면 점수가 높을 때 10%를 넘어요.
34. 막대 아래 눈금 숫자는 실제 점수 위치와 100 위치에 적어요. 두 숫자가 겹칠 만큼 가까우면(실제 점수가 85점을 넘으면) 위아래 두 줄로 적어요.
35. "입력 고치기"는 점수 해부 화면의 맨 아래(스크롤 영역 안)에 뒀고, 아래 고정 영역에는 주 버튼만 있어요. 이유: 핵심 화면의 읽는 영역을 넓히려고요.
36. 빈 상태 문구를 더 나눴어요. 이유: 지시서의 문구가 맞지 않는 경우에 사실과 다른 말을 하지 않으려고요.
    - 고민이나 자신 없음 표시만 있으면 "찍었다고 표시한 문항이 없어서 나눠 볼 것이 없어요. N점 그대로예요."
    - 찍음 표시는 없는데 원인을 표시했으면 "찍었다고 표시한 문항이 없어요. N점 그대로예요."
    - 찍음 표시가 있는데 맞힌 것이 없으면 "찍었다고 표시한 문항에서 나온 점수는 없어요."
    - 원인을 골랐는데 실수가 없으면 "실수라고 표시한 오답이 없어요"
    - 원인을 일부만 골랐으면 "원인을 표시하지 않은 문항이 N개 있어요"와 링크
37. 확정 컷일 때의 문구는 "컷과 같은 점수예요.", "컷보다 위예요."예요. 이유: 한 숫자에는 "범위 안"이라는 말이 맞지 않아요.
38. 찍기 운을 평균으로 본 점수는 지시서대로 등급컷 상자의 둘째 줄에만 나와요. 목표 등급을 고르지 않았거나 컷 자료가 없으면 나오지 않아요. 첫 줄이 "남았어요"가 아닐 때(범위 안이나 위)는 둘째 줄 끝을 "N~M점 남았어요"로 적어 혼자서도 뜻이 통하게 했어요.
39. 계단의 "다시 풀 문항"은 틀린 문항과 찍었다고 표시하고 맞은 문항이에요. 찍었다고 표시하고 맞은 문항은 1.1부터 답을 다시 받지 않고 풀이를 끝까지 써 봤는지 스스로 고르게 해요(40번). 이유: 지시서의 예시 이유 문장이 그 문항을 다시 볼 대상으로 삼고 있어서요.
40. 재풀이 기록 라벨(1.1, 작업 지시서 1의 3-6과 3-10). 틀린 문항을 다시 풀어 맞혔으면, 정답을 먼저 봤거나 "이미 했어요" 경로일 때 "정답 확인 후 다시 맞힘"이 먼저예요. 그 밖에는 처음 맞은 차례("답 맞춰 보기"를 누른 차례 가운데 처음 맞은 차례, firstCorrectAttempt)가 첫 차례면 "다시 풀어 맞힘"(원인이 실수였으면 "실수로 표시함, 다시 풀어 맞힘"), 둘째 차례 이후면 "풀어"라는 말을 빼고 "N번째로 넣은 답이 맞음"(실수였으면 "실수로 표시함, N번째로 넣은 답이 맞음")이고 결과 문장은 "N번째로 넣은 답이 맞았어요."예요. 맞힌 뒤에 다시 넣어 틀리면 최근 결과를 따라 "다시 풀었지만 답이 다름"이에요. 찍었다고 표시하고 맞은 문항은 "이 문항은 찍었다고 표시했고, 채점해 보니 맞았어요. 풀이를 끝까지 써 봤나요?"에 "끝까지 풀었어요", "풀어 봤는데 막혀요", "아직 안 풀어 봤어요"로 답해요. 결과 문장은 "끝까지 풀었다고 표시했어요.", "막힌다고 표시했어요."이고, 라벨은 "찍음 표시 정답, 끝까지 풀었다고 표시함", "찍음 표시 정답, 막힌다고 표시함"이에요. 정답 대조가 아니므로 정답색, 오답색, 맞음과 틀림 기호 없이 중립 표시로 보여 줘요. 선택은 다시 바꿀 수 있고 라벨은 마지막 선택을 따라요(79번). 이유: 5지선다는 틀린 보기를 지워 가며 맞힐 수 있어서 여러 번 만에 맞힌 것을 "다시 풀어 맞힘"이라고 하면 실제보다 좋게 읽혀요. 찍음 표시 정답은 넣었던 답이 맞았다는 것을 학생이 이미 알아서, 답을 다시 넣게 하면 같은 답으로 "다시 풀어 맞힘"이 찍혀요. 1.0에서는 지시서의 3종만 썼고 몇 번째에 맞혔는지는 기록 값으로만 남겼어요.
41. 틀린 재풀이의 결과 문장은 "이번에도 답이 달랐어요."예요. "이 유형을 계단에 남겨 둘게요."라는 말은 어디에도 쓰지 않아요(1.1, 작업 지시서 1의 3-6). 이유: 계단의 순서와 숫자는 다시 풀기 결과로 바뀌지 않아서 그 말이 사실과 달라요. 1.0에서 찍음 표시 정답을 다시 풀어 틀렸을 때 쓰던 "이번에는 답이 달랐어요..."는 찍음 표시 정답이 답을 다시 받지 않게 되면서 없어졌어요.

### 화면 이동과 기록

42. 탭 "이번 시험"은 늘 시작 화면으로 가요. 시작 화면의 "이어서 보기"가 마지막으로 보던 기록으로 가요. 지금 보는 기록이 없으면(지금 보던 기록을 지운 경우) 남은 기록 가운데 가장 최근에 만든 것을 열어요. 이유: 지시서 8장 (1)의 "지난 기록이 있으면 이어서 보기"를 글자대로 따랐어요.
43. "예시 결과 보기"는 저장하지 않는 기록으로 열어요(주소 #/demo/anatomy). 기록 목록에 넣지 않고, "입력 고치기" 자리에 "시험 고르기"를 둬요.
44. 같은 시험을 다시 고르면 한 번도 채점하지 않은 기록이 있을 때 그 기록을 이어 써요. 채점한 적이 있는 기록만 있으면 새 기록을 만들어요. 이어 쓸 때 "채점은 아직인가요?"의 답은 방금 고른 것으로 바꿔요. 이유: 잘못 눌렀다가 다시 고른 것을 받아 주려고요. 처음에는 "이미 했어요"를 한 번 고르면 되돌릴 수 없었는데, 화면에서 고른 것과 다른 내용이 기록에 남았어요(세 번째 검토). 테스트 기기에서는 50번과 92번을 따라요(대기 중에는 이어 쓰지 않아요).
45. 기록과 맞지 않는 주소는 알맞은 화면으로 돌려보내요(미입력이 있는데 #/score 를 열면 답 입력으로).
46. 지금 보던 기록을 지우면 다른 기록으로 옮겨 가지 않고 "지금 보는 기록 없음" 상태가 돼요. 남은 기록은 시작 화면의 "이어서 보기"나 기록 탭에서 직접 눌러야 열려요. 이유: 별도 검토에서 기록을 지운 뒤 뒤로 가면 다른 시험의 결과가 열리는 것을 찾았어요.

### 테스트 진행자용

47. 측정 기록은 진행자가 "테스트 시작하기"를 눌렀을 때만 남겨요. 이유: 평소 사용에서는 아무것도 재지 않으려고요.
48. 참가자 코드 칸은 3글자까지만 받고 P와 숫자 2자리 형식만 통과시켜요. 이유: 이름이 들어갈 수 없게 하려고요.
49. 진행자가 고른 "시험"은 계획한 시험으로 기록해요. 참가자는 실제 화면에서 시험을 직접 골라요. 다른 시험을 고르면 측정 기록에 표시돼요. 이유: 시험 선택부터 첫 점수까지를 재야 해서 시험 선택 화면을 건너뛸 수 없어요.
50. 새 참가자를 시작하면 앞 사람의 기록이 "이어서 보기"로 열리지 않게 지금 보는 기록을 비워요. 테스트 중에는 이번 참가자가 만든 기록(측정을 시작한 뒤에 만든 기록)만 이어 쓰고, "이어서 보기"도 이번 참가자의 기록만 열어요(지금 보는 기록이 이번 참가자의 것이면 그 기록, 아니면 측정에 묶인 기록, 그 기록이 지워졌으면 이번 참가자가 만든 기록 가운데 가장 최근 것). 저장 값이 망가져 시작 시각을 읽지 못한 측정에서는 언제 시작했는지 알 수 없으므로 측정에 묶인 기록만 이번 참가자의 것으로 봐요. 참가자를 마치거나 시험 기록을 지울 때 최종 제출한 답을 측정 기록에 옮겨 둬요. 끝난 측정은 그 사본만 써서, 뒤에 누가 그 시험 기록을 고치거나 지워도 최종 답과 남은 오입력이 바뀌지 않아요. 시험 기록을 지운 뒤에도 정답지 대조를 할 수 있어요. 1.1부터 측정이 진행 중이면 기록 탭에도 이번 참가자의 기록만 보이고 "이 기기의 기록 모두 지우기"를 숨겨요. 참가자를 마친 뒤 다음 참가자를 시작하기 전에는 기록 탭에 기록을 보여 주지 않고 "테스트 기기예요. 기록은 진행자용 화면에서 확인해요."만 보여 줘요(84번). 이때 시험을 골라도 앞 참가자의 채점 전 기록을 이어 쓰지 않아요(92번). 진행자가 측정 기록을 모두 지우면 평소대로 돌아가요.
51. 답 입력 시간은 답 입력 화면에 처음 들어온 때부터 모든 문항이 처음 다 찬 때까지예요. 단답형 입력 횟수는 숫자를 누른 횟수가 아니라 확정한 횟수예요.
52. 답지는 쉼표, 줄바꿈, 빈칸 어느 것으로 구분해도 읽고, 안 푼 문항은 x나 "안 풂"으로 적어요.
53. 진행자가 고른 입력 방식이 주소의 input 값보다 우선이에요. 이유: 테스트 도중 주소 때문에 방식이 바뀌면 비교가 깨져요.

### 세 번째 검토 뒤에 더한 것

61. 테스트 중에 측정에 묶이지 않은 기록(기기에 남아 있던 다른 기록)의 화면을 열면 화면 진입 기록에 "other:화면이름"으로 적고, 그 시각은 답 입력 시작, 첫 점수, 표시 화면에 머문 시간에 쓰지 않아요. 진행자용 화면에 들어온 것도 test 로 적어요. 이유: 앞 기록의 점수 화면을 먼저 열면 "시험 선택부터 첫 점수까지"가 음수로 나왔고, 표시 화면에서 진행자용 화면에 다녀오면 그 시간이 표시 화면에 머문 시간에 들어갔어요.
62. 참가자가 측정 중에 다른 시험 기록으로 옮겨 가면(시험을 다시 고르거나, 자기가 만든 채점 전 기록을 기록 화면이나 "이어서 보기"로 다시 열면) 측정도 그 기록으로 옮겨요. 앞 기록에서 재던 값은 따로 넣어 두었다가 그 기록으로 돌아오면 이어 써요. 옮겨 간 횟수는 측정 카드와 CSV(exam_reselects)에 적어요. 채점까지 마친 측정은 옮기지 않아요. 그 뒤에 새로 시작한 기록은 재지 않고, 채점한 기록을 지워도 마친 측정값과 최종 답은 남아요. 정답 공개 전 시험은 저장해도 채점한 것이 아니라서, 그 뒤에 다른 시험을 고르면 측정이 옮겨 가요. 이유: 앞 시험에서 누른 횟수가 새 시험의 문항별 입력 횟수에 섞였어요. 처음 고칠 때는 옮길 때마다 값을 비웠는데, 네 번째 검토에서 원래 기록으로 돌아오면 일부만 잰 값이 온전한 값처럼 나오는 것과, 채점한 기록을 지우고 새로 시작하면 마친 측정값이 지워지는 것을 찾아 지금처럼 바꿨어요.
63. 표시 화면의 단답형 번호는 같은 폭의 칸으로 여러 줄에 놓아요(지시서는 "한 줄로"). 기본 글자 크기에서는 한 줄에 네 칸이고 예시 시험 A의 9문항은 세 줄이에요. 이유: 9문항에 터치 영역 48px과 간격 8px을 주면 496px이 필요한데 본문 폭은 350px이에요. 가로로 미는 한 줄은 뒤쪽 번호가 가려져서 쓰지 않았어요. 처음에는 내용 폭대로 놓고 줄을 넘겼는데, 네 번째 검토에서 "자신 없음"이 붙으면 칸이 넓어져 뒤 번호가 밀리고, 같은 자리를 다시 누르면 옆 번호에 표시가 붙는 것을 찾아 칸의 폭을 고정했어요. 다섯 번째 검토에서는 글자를 키우면 "자신 없음"이 붙을 때 줄이 높아져 아래가 밀리는 것을 찾아, 번호 줄과 "자신 없음" 줄의 높이를 늘 잡아 두고 칸의 최소 폭을 글자 크기에 맞췄어요(4.5rem. 글자를 키우면 한 줄의 칸 수가 줄어요).
64. 카드는 지시서대로 표면색으로 그려요. 카드 안의 입력 칸도 지시서대로 표면색이고 테두리(윤곽색, 표면색 위 3.10:1)로 구분해요. 카드 안의 안내문만 배경색으로 바꿔서 구분하고, 막대 무늬의 빈 바탕은 놓인 자리의 색을 따라요. 탭 글자, 칸 안의 "안 풂"과 "미입력", 카드 안의 작은 제목은 글자 6단계의 굵기(보조와 캡션은 400)에 맞췄어요.
65. 5행 방식에서 안 풂으로 둔 문항은 접근성 이름에 그 상태를 넣어요. 번호 버튼은 "2번, 넣은 답 안 풂, 안 풂 또는 입력 지우기", 단답형 줄은 "16번 답 안 풂, 눌러서 고치기"예요. 이유: 화면 낭독기로 들었을 때 안 풂과 미입력이 같게 들렸어요.
66. verify는 검사의 최소 기준을 따로 정해 두고, 못 미치면 해당 항목을 실패로 적어요. 기준은 통과한 단위 테스트 202개, 화면 상태 334개, 작은 화면 상태 123개(그 가운데 스크롤 없이 들어와야 하는 답 입력 상태 68개), 실제로 돈 화면 테스트 125개(그 가운데 앱용 묶음 화면 테스트는 꼭 40개), 정답 노출 검사(화면을 읽는 검사 48번, 두 빌드를 견준 화면 25곳, 대조 검사 4번), 캡처 묶음마다 69장이에요. 1.0의 기준(단위 테스트 149개, 화면 상태 300개, 작은 화면 상태 100개와 그 가운데 64개, 화면 테스트 78개, 화면을 읽는 검사 44번, 캡처 64장)에서 1.1과 앱용 묶음의 측정값으로 올렸어요. 꼭 있어야 하는 단위 테스트의 이름(56번)과 기다리지 않는 좌표 누름 화면 테스트 4개의 이름도 따로 확인해요(빠지면 1번, 2번 항목이 실패해요). 검사 기록에 결과 칸이 빠져 있어도 0건으로 세지 않고 실패로 적어요. 건너뛴 테스트(단위 테스트와 화면 테스트 모두)는 통과로 세지 않고 실패로 적어요. 요청 기록은 실제로 돈 화면 테스트마다 하나씩 있어야 하고, 알림 권한을 요청한 횟수도 그 기록마다 숫자로 있어야 해요. 실행 단계(빌드, 화면 검사 등)가 실패로 끝나면 결론 문장에도 실패로 적어요. 화면 검사는 실행할 때마다 지금 폴더의 빌드로 서버를 새로 띄우고, 포트(기본 4173, 4174)에 이미 떠 있는 서버가 있으면 다시 쓰지 않고 실패로 끝나요(옛 빌드를 재고 통과로 적는 일을 막으려고요). 화면 테스트만 따로 돌릴 때 쓰는 스위치(SA_REUSE_SERVER=1)가 켜져 있어도 verify는 따르지 않아요. verify는 시작할 때 docs/검증결과.md를 "검증이 끝나지 않았어요"로 바꿔 두고, 보고서를 만들다 오류가 나면 그 까닭을 적은 실패 보고서를 남겨요(도중에 멈춰도 앞 실행의 "통과"가 남지 않게요). 이유: 검사가 줄거나 빠져도 "통과"로 적히는 일을 막으려고요. 테스트를 일부러 더하거나 줄였다면 scripts/verify.mjs 의 이 값도 함께 고쳐야 해요.

67. 기록 화면의 열기와 지우기 버튼은 접근성 이름에 날짜와 점수를 함께 넣고("예시 시험 A 기록 열기, 2026년 11월 22일, 78점"), 삭제 확인 대화상자에도 어느 기록인지 적어요. 시험, 날짜, 점수가 모두 같은 기록이 또 있으면 목록과 이름에 넣은 시각(시, 분)도 적고, 분까지 같으면 초도 적어요. 초까지 같은 기록은 구분되지 않는데, 사람이 화면을 눌러서는 생기기 어려워요. 이유: 같은 시험의 기록이 여러 건이면 화면 낭독기로는 구분되지 않았어요.
68. 정답 공개 전에 저장해 둔 기록은 정답이 공개된 뒤에 열면 표시 화면으로 가고, 기록 화면에는 "채점 전"으로 적어요. 이유: 저장할 때의 안내문이 "공개되면 여기서 바로 채점돼요"라고 말해요. 처음에는 "입력 중"으로 적고 입력 확인 화면으로 보냈어요.

69. 저장된 측정 기록의 시각이 날짜로 쓸 수 없는 값이면 읽을 때 비워요. 시작 시각도 마찬가지라서 카드에는 "아직 없음"으로 보이고, 내보낸 CSV에서는 빈칸, JSON에서는 null이에요. 읽지 못한 경우(0 이하로 읽힌 경우)만 그렇고, 0보다 크지만 엉뚱하게 작은 값(예: 1)은 날짜로 읽혀 그대로 적혀요. 내보낼 글자를 만들지 못하면 "파일로 저장하지 못했어요. 복사를 써 주세요."나 "복사하지 못했어요. 파일 저장을 써 주세요."를 보여 줘요. 이유: 망가진 값 하나 때문에 다른 참가자의 기록까지 안내 없이 꺼내지 못했어요.
70. 고른 칩(시간 선택지, 목표 등급, 진행자용 선택지)은 테두리가 굵어지고 체크 표시가 붙지만 폭은 그대로예요. 체크 표시와 틈만큼 양옆 여백을 줄이고 글자 굵기는 바꾸지 않아요(전에는 600으로 굵게 했어요). 이유: 고르면 폭이 20px쯤 늘어 옆 칩이 밀렸고, 같은 자리를 다시 누르면 옆 선택지가 골라졌어요.

### 1.1에서 정한 것

71. 키패드 방식의 규칙(커서 이동, 잠금, 지우기, 확정하지 않은 숫자)을 src/logic/keypad.ts 의 순수 함수(reduceKeypad)로 떼었어요. 화면은 그 결과대로 답을 저장하고 화면을 옮기기만 해요. 단답형에서 누르고 있는 숫자도 이 함수 안에서 다뤄요. 이유: 작업 지시서 1의 3-2가 규칙을 화면 코드에서 떼어 단위 테스트를 붙이라고 했고, 무작위 검사(누름 열 1만 2천 개)를 화면 없이 돌리려고요.
72. 답을 넣어 키패드가 잠겼을 때의 "지우기"는 단답형도 저장된 답을 한 번에 지우고 잠금을 풀어요(5지선다와 같아요). 빈칸 없이 연 화면의 잠금에서는 "지우기"도 받지 않아요(87번). 3-3의 "한 자리씩 지운다"는 잠기지 않은 칸(고치기로 들어와 답을 불러온 칸)에서만 써요. 이유: 잠금 규칙이 "그 칸의 답을 지우고 풀린다"이고, 한 자리씩 지우게 두면 잠금이 풀린 뒤 이어 누른 숫자와 "다음"이 답이 든 칸을 바꿔서 3-2 (j)의 "답이 든 칸의 값이 바뀌는 것은 고치기로 들어온 뒤의 첫 입력뿐"이 깨져요.
73. 고치기로 들어와 불러온 답의 숫자를 다 지우고 "다음"을 누르면 1.0처럼(19번) 그 칸의 답을 지우고 "N번이 비어 있어요..."를 보여 줘요. 숫자를 하나도 누르지 않고 "다음"을 누른 것(들어 있던 답을 넣은 것으로 봐요)과는 달라요. 이유: 큰 칸이 빈 것을 보고 누른 "다음"에 옛 답을 넣으면 화면과 기록이 어긋나요.
74. 고치기로 들어와 아직 답을 넣기 전에는 안내문 자리에 "N번을 고치는 중이에요."와 "K번부터 이어서 넣기"를 보여 줘요. 그 칸을 지운 뒤에도("N번 답을 지웠어요.") 같은 버튼이 남아요. 빈칸이 없으면 버튼 없이 안내문만 보여 줘요. 이유: 잘못 눌러 들어왔을 때 아무것도 바꾸지 않고 돌아가는 길이 늘 보이게 하려고요.
75. 잠긴 칸을 다시 누르면 잠금을 풀고 그 칸을 고치기로 들어온 것으로 봐요. 잠기지 않은 지금 칸을 다시 누르면 아무것도 바꾸지 않아요. 이유: 방금 넣은 답을 다시 고치고 싶을 때 가장 자연스러운 동작이 그 칸을 누르는 것이에요.
76. 이어서 들어온 빈칸에서 "지우기"를 눌렀는데 앞 번호도 빈칸이면, 앞 번호로 가기만 하고 아무것도 지우지 않아요(안내문 없음). 1번에서는 "지울 답이 없어요."를 보여 줘요. 이유: 지시서는 "앞 번호로 가서 그 답을 지운다"만 정했고, 지울 답이 없는데 "지웠어요"라고 하면 사실과 달라요.
77. 안내문 자리의 버튼("M번도 고치기", "K번부터 이어서 넣기")을 누르면 그 자리를 연달아 누르기 보호에 넣어요. 잠금으로 버튼이 나타나는 것은 지시서대로 넣지 않아요. 이유: 버튼을 누르면 같은 자리에 다른 버튼이 올 수 있어서(고치기 안내의 "이어서 넣기") 두 번 누르면 원하지 않은 버튼이 눌려요. 6번의 "아래 버튼이 다른 버튼이 됨"과 같은 경우예요.
78. 잠긴 키는 disabled 대신 aria-disabled 로 알리고 점선 테두리와 보조 글자색으로 흐리게 보여 줘요. 눌러도 아무것도 들어가지 않아요. 이유: 화면 낭독기에 쓸 수 없는 상태로 전하면서, 누른 것은 앱이 받아서 무시하려고요(브라우저마다 disabled 버튼의 누름을 다르게 다뤄요). 색 대비는 보조 글자 기준(4.5:1 이상)을 지켜요.
79. 찍음 표시 정답의 스스로 확인에서 "아직 안 풀어 봤어요"를 고르면 기록을 남기지 않고 다음으로 넘어가며, 앞서 남긴 확인 기록도 지워요. 이유: "선택은 다시 바꿀 수 있고 라벨은 마지막 선택을 따른다"에 맞추려면 마지막 선택이 "아직"일 때 남은 라벨이 없어야 해요.
80. 1.0에서 찍음 표시 정답을 다시 풀어 남긴 답 기록("다시 풀어 맞힘" 등)은 계단 카드의 "다시 푼 기록"에 보여 주지 않아요. 기록 값은 지우지 않아요. 이유: 작업 지시서 1이 이 문항에 "다시 풀어 맞힘" 계열 라벨과 "정답 확인 후" 라벨을 쓰지 말라고 했어요.
81. 찍기 운 평균의 반올림 전 값(luckAverage)은 분자를 분모로 나눈 값으로 두되, 화면의 "약 N점"과 둘째 줄의 남은 점수는 정수 식으로만 계산해요. 반올림 전 값은 테스트와 설명에만 써요.
82. 받지 않은 누름은 측정 중에 버린 누름 하나당 1씩 세요. 빈 바탕을 누른 것도 버렸으면 세고(알림은 누를 수 있는 요소 위일 때만 띄워요), 진행자용 화면, 예시 결과, 측정에 묶이지 않은 기록의 화면에서 버린 누름은 세지 않아요. 측정 기록 한 건에 수 하나로 두고(시험 기록별로 나누지 않아요) 측정 카드의 "받지 않은 누름"과 CSV의 discarded_taps 에 적어요. 이유: 작업 지시서 1이 "버린 누름 하나당 1씩" 세라고 했어요.
83. 버린 누름 알림은 2초 동안 화면 위쪽부터 내려가며 누를 수 있는 요소와 겹치지 않는 첫 자리에 고정 위치로 띄우고, 알림 자체는 누름을 받지 않아요. 화면 낭독기에는 보이는 알림 대신 미리 붙여 둔 알림 영역(aria-live=polite, role 은 두지 않음, 90번)으로 한 번 전하고, 바텀시트나 대화상자가 열려 있으면 그 안에 미리 둔 영역을 써요. 같은 보호 구간(화면이 바뀌어 막기 시작한 때부터 풀릴 때까지)에서는 한 번만 띄워요. 이유: 화면 구성을 밀지 않고 버튼을 가리지 않아야 하고, 대화상자 밖을 읽지 않는 화면 낭독기에도 전해져야 해요.
84. 참가자를 마치면 지금 보는 기록을 비우고, 대기 중(측정 기록이 있고 진행 중인 측정이 없음)에는 시작 화면의 "이어서 보기"가 어떤 기록도 열지 않아요. 기록 탭에는 안내만 보이고 "준비 중인 기능" 목록과 "테스트 진행자용" 링크는 그대로 둬요. 이유: 지시서는 기록 탭만 적었지만, 학생이 보는 어느 화면에도 앞 참가자의 점수가 나오지 않게 하려면 이어서 보기도 막아야 해요. 진행자는 그 링크로 진행자용 화면에 가요.
85. 문구는 지금처럼 src/strings.ts 한 파일에 두되 내보내는 묶음을 나눴어요(S, S_ROWS, S_TEST, S_TOOLS, S_APP). 사용성 테스트 도구(진행자용 화면, 5행 방식 화면, "준비 중인 기능" 목록과 진행자용 링크)는 src/tools 로 모아, 빌드 설정의 #tools 별칭과 __SA_TOOLS__ 상수로 넣고 뺄 수 있게 했어요. 일반 웹 빌드와 단일 HTML은 모두 싣고 동작은 그대로예요. 이유: 앱 배포용 묶음에서는 이 화면들의 코드와 글자를 숨기는 것이 아니라 빼야 해요(작업 지시서 1의 6-1).
86. 윈도우에서 verify 를 돌릴 수 있게 고쳤어요. npm.cmd 와 npx.cmd 는 셸로 실행하고, .gitattributes 로 작업 폴더의 줄바꿈을 모든 운영체제에서 LF로 두고, 화면 코스는 클립보드에서 읽은 줄바꿈을 맞춘 뒤 견줘요. 브라우저 버전 확인도 화면 검사와 같은 브라우저(Playwright 브라우저가 없으면 시스템 크롬)를 띄워요. 이유: 1.1 작업은 윈도우 11에서 했고, 1.0의 verify 는 리눅스에서만 돌아서 윈도우에서는 모든 단계가 실패했어요(npm.cmd 실행 오류, CRLF로 받은 문서, 윈도우 클립보드의 줄바꿈). 앱용 묶음의 SHA-256 이 운영체제에 따라 달라지지 않게 하는 데도 필요해요.

### 1.1 별도 검토 뒤에 정한 것

87. 빈칸 없이 연 화면의 잠금에서는 "지우기"도 받지 않아요(모든 키가 흐리게 잠겨요). 칸을 눌러야 풀려요. 이유: 학생이 고른 칸이 없는데 지우기를 받으면 고르지 않은 마지막 문항부터 지워지고, 이어 누르면 앞 번호가 차례로 지워졌어요(1.1 별도 검토 3번). 커서는 마지막 문항에 두고 들어온 길은 지시서대로 "이어서"예요.
88. 큰 번호 위의 이름은 상태마다 달라요: "지금 넣을 문항"(이어서, 빈칸 누름), "고치는 문항"(고치기로 들어와 아직 잠기지 않음), "방금 넣은 문항"(답을 넣고 잠김), "마지막 문항"(빈칸 없이 열어 잠김). 이유: 잠긴 동안 "지금 넣을 문항"이라고 하면 키를 받지 않는다는 안내와 어긋났어요(1.1 별도 검토 3번). 지시서 8장의 "지금 넣을 문항"은 늘 넣을 문항이 있던 1.0의 흐름에서 정한 이름이라, 1.1에서 생긴 상태에만 다른 이름을 썼어요.
89. 키패드 위 안내문은 화면 낭독기에 늘 붙어 있는 알림 영역 하나(role=status, 보이지 않음)로 전하고, 보이는 안내문은 낭독에서 빼요(aria-hidden, 훑어 읽을 때 같은 문장을 두 번 듣지 않게). 화면을 열 때 나오는 안내(빈칸 없음)는 알림 영역을 빈 채로 먼저 그리고 다음 그림 차례에 채워서 전해요. 잠긴 키를 누르면 그 알림 영역을 잠깐 비웠다가 다시 채워 잠금 안내를 한 번 더 전해요(입력은 그대로 받지 않아요). 이유: 글자를 담은 채 새로 붙는 알림 영역은 화면 낭독기가 읽지 않는 경우가 많고, 잠긴 키를 눌러도 아무 소리가 없으면 왜 안 듣는지 알 수 없어요(1.1 별도 검토 2번).
90. 버린 누름 알림을 전하는 알림 영역(aria-live=polite)도 미리 붙여 둬요. 앱이 시작할 때 문서 끝에 하나를 만들고, 바텀시트와 대화상자는 열릴 때부터 자기 안에 하나씩 둬요. 알림을 띄울 때 열린 대화상자가 있으면 그 안의 영역에, 없으면 문서 끝의 영역에 글자를 넣고, 알림이 닫히면 비워요. 이유: 89번과 같아요. 다른 안내문의 role=status 와 겹치지 않게 이 영역에는 role 을 두지 않았어요.
91. 잠금, 고치기, 빈칸 없음, 지웠음 안내는 정보 모양(왼쪽 줄이 윤곽색)으로, 범위 밖 숫자, 빈칸, 확정하지 않은 숫자, 지울 답 없음 안내는 지금처럼 경고 모양(왼쪽 줄이 경고색)으로 보여 줘요. 이유: 잠금 안내가 오류처럼 보였어요(1.1 별도 검토 7번).
92. 테스트 기기의 대기 중(참가자를 마친 뒤, 다음 참가자를 시작하기 전)에는 시험을 골라도 채점 전 기록을 이어 쓰지 않고 새 기록을 만들어요. 이유: 대기 중에 같은 시험을 고르면 앞 참가자의 채점 전 기록(넣은 답 전부)이 열리고 채점까지 할 수 있었어요(1.1 별도 검토 1번). 앞 참가자의 기록은 앱이 스스로 지우지 않고 그대로 둬요(학생이 보는 화면에는 나오지 않고, 지우는 것은 진행자가 테스트를 마친 뒤 해요). 진행자용 화면의 최종 답과 답지 대조는 참가자를 마칠 때 옮겨 둔 사본을 써서(50번) 이 기록이 없어도 돼요.
93. 고치기로 들어와 확정하지 않은 숫자를 버렸다는 안내(20번)가 뜨면 그 안내가 "N번을 고치는 중이에요." 자리를 차지해요. "K번부터 이어서 넣기" 버튼은 그대로 남고, 다음 누름에서 안내가 사라지면 다시 "고치는 중"이 보여요. 이유: 안내문 자리는 하나라서 방금 일어난 일(버린 숫자)을 먼저 알려요.
94. 찍음 표시 정답의 "아직 안 풀어 봤어요"는 고르는 선택지(라디오)가 아니라 다음 문항으로 넘어가는 버튼으로 둬요. 앞의 두 선택지만 라디오예요. 이유: 고르면 다음 문항으로 넘어가고 선택으로 남지 않아서, 라디오로 두면 화면 낭독기 사용자에게 예상 밖이었어요(1.1 별도 검토 8번).
95. "K번부터 이어서 넣기"로 온 빈칸에서 "지우기"를 누르면 K-1번으로 가서 그 답을 지워요. 고친 칸(N번) 바로 다음이 K번이면 K-1번은 방금 고친 칸이라 방금 넣은 답을 지우는 길이에요. N번과 K번 사이에 답이 든 칸이 있으면 K-1번은 학생이 방금 넣은 답이 아닌 칸이에요(예: 12번을 넣을 차례에 9번을 고친 뒤 "12번부터 이어서 넣기"를 누르고 지우면 11번이 지워져요). 지시서의 "이어서"(그 버튼으로 온 경우를 포함)대로 뒀어요. 사용성 테스트에서 보고 정할 수 있게 제안 17번에 적었어요(1.1 별도 검토 7번).
96. 빈칸을 직접 눌러 들어온 칸에는 원래 넣던 칸으로 돌아가는 버튼이 없어요. 지시서가 버튼을 고치기와 잠금에서만 정했어요. 제안 18번에 적었어요(1.1 별도 검토 7번).
97. 3-2 (f)의 단위 테스트는 "다 찬 상태에서 고치면 입력 확인으로 넘어간다"까지만 보고, 넘어간 뒤 이어 누른 것이 9번이나 입력 확인의 버튼에 닿지 않는 것은 화면 테스트(e2e/rhythm.spec.ts, 기다리지 않는 좌표 누름)가 확인해요. 이유: 그 보호는 키패드 규칙이 아니라 화면 전체를 잠깐 막는 누르기 보호가 맡아서, 규칙 함수만으로는 검사할 수 없어요(1.1 별도 검토 4번).
98. 범위 밖 조건 검사(conditions.spec.ts)에 1.1의 고치는 중과 잠금 상태를 더했어요. 세로 조건(360x640 글자 20px와 24px, 360x560, 320x568)에서는 지금처럼 키패드와 지금 칸이 화면 안에 있는지 확인해요. 가로 640x360에서는 키패드가 화면 아래로 나간 높이를 재서 적기만 해요(단답형의 고치는 중과 잠금에서 9px, 객관식 잠금에서 0px). Playwright 가 누르기 전에 화면 틀(.app)을 밀어 둔 것은 되돌린 뒤 재요. 화면 틀은 손가락으로 밀 수 없는데, 밀린 채로 재면 잘린 높이가 작게 나왔어요(1.1 재검토). 이유: 가로 화면은 지원 범위(세로 360~430px) 밖이고 이 조건들은 결과만 적어요(58번). 맞추려면 가로 화면용 배치가 필요해서 제안 16번에 적었어요(1.1 별도 검토 6번).
99. 재풀이 키패드와 답 고치기 시트의 안내문도 89번처럼 늘 붙어 있는 알림 영역으로 전하고, 보이는 안내문은 낭독에서 빼요. 재풀이의 결과 카드(맞춰 본 결과, 스스로 확인한 결과)는 늘 붙어 있는 알림 영역(role=status) 안에 넣어, 카드가 나타날 때 전해요. 이유: 89번과 같아요. 입력 화면만 고치고 같은 구조의 재풀이 키패드와 시트는 그대로였어요(1.1 재검토). 키패드 밖의 안내문(입력 확인의 미입력 경고, 시험 선택과 표시 화면의 안내, 진행자용 화면과 기록 화면의 안내, 좌표 복사 결과)은 1.0 그대로 글자를 담은 채 붙는 알림 영역이에요. 실제 화면 낭독기에서 읽히는지 보고 바꿀 수 있게 제안 21번에 적었어요.

## 3. 제안 (구현은 지시서대로 두었어요)

1. 키패드 방식에서 이미 넣은 칸을 고친 뒤에는 다음 문항이 아니라 첫 빈칸으로 돌아가기. 지금은 지시서대로 다음 문항으로 가서, 화면을 안 보고 이어 누르면 다음 칸을 덮어쓸 수 있어요. 사용성 테스트에서 남은 오입력으로 확인해 보세요. 처리: 1.1에서 다시 설계해 반영했어요(작업 지시서 1의 3-2). 첫 빈칸으로 돌아가는 대신, 고친 칸에 머물고 키패드를 잠근 뒤 학생이 버튼으로 다음 할 일을 골라요(4장 3-2).
2. 키패드 방식의 "지우기"를, 지금 칸에 답이 들어 있을 때는 그 칸을 지우게 하기. 지금은 지시서대로 늘 한 칸 뒤를 지워서, 칸을 눌러 간 문항에서 누르면 눈에 보이는 큰 번호가 아니라 그 앞 문항이 지워져요(안내문으로 알려 줘요). 처리: 1.1에서 반영했어요(3-3). 눈에 보이는 지금 칸부터 지워요.
3. "없어요"를 표시가 하나도 없을 때만 보여 주거나, 표시가 있을 때는 지우기 전에 한 번 묻기. 지금은 붙여 둔 표시가 말없이 지워져요. 처리: 1.1에서 반영했어요(3-4). "없어요, 채점하기"와 "채점하기"를 한 버튼으로 합치고, 표시를 지우지 않아요.
4. 찍기 운 평균의 0.2를 시험 데이터의 보기 수로 계산하기(1 나누기 보기 수). 보기가 5개가 아닌 시험이 들어오면 0.2가 맞지 않아요. 처리: 1.1에서 반영했어요(3-5). 정수로 계산해요. 보기 수가 5가 아닌 시험의 화면 지원은 범위 밖이에요.
5. 찍어서 맞혔다고 표시한 문항의 재풀이 라벨을 따로 두기. 그 문항은 자기 답이 맞았다는 것을 이미 알고 있어서, 같은 답을 다시 넣어도 지금은 지시서대로 "다시 풀어 맞힘"으로 적혀요. 답을 넣는 대신 "풀이를 써 봤어요" 같은 자기 확인으로 바꾸는 방법도 있어요. 처리: 1.1에서 반영했어요(3-6). 답 입력 대신 스스로 확인하게 했어요.
6. 막대의 "표시 없이 맞힌 점수"에는 고민 표시 문항도 들어가요. 이름을 "찍음 표시 없이 맞힌 점수"로 바꾸면 더 정확해요. 처리: 1.1에서 반영했어요(3-7).
7. 시험 JSON에 시행일 칸을 더해 목록 순서와 화면 표시에 쓰기. 처리: 1.1에서 반영했어요(3-8). 예시 시험에는 넣지 않았어요.
8. 단답형 키패드의 두 줄 배열과 전화기 배열을 사용성 테스트에서 견줘 보기. 큰 화면에서만 전화기 배열을 쓰는 방법도 있어요. 처리: 바꾸지 않았어요. 사용성 테스트에서 볼 질문으로 docs/사용성테스트_진행안내.md 8장에 넣었어요.
9. 연달아 누르기 보호의 시간(0.5초), 거리(누른 자리에서 가로세로 24px), 숫자 키를 버리지 않는 판단, 마지막 문항 뒤에 화면 전체를 막는 판단을 사용성 테스트에서 확인하기. 화면이 바뀐 직후 0.5초 안에 같은 자리에 온 5지선다 답 키는 버려지고, 숫자 키는 버려지지 않아요. 버린 누름을 화면에 알려 주는 방법도 있어요. 처리: 1.1에서 버린 누름을 알리고(누를 수 있는 요소 위일 때만) 측정 중에는 세게 했어요(3-9). 보호의 시간, 거리, 대상은 바꾸지 않았어요. 시간과 거리를 정하는 것은 사용성 테스트의 "받지 않은 누름" 수와 관찰로 볼 일이에요.

## 6. 시험 당일 경로

작업 지시서 3이에요. 앱을 새로 내지 않고도 시험 날 정답과 등급컷을 넣을 수 있게 시험 파일 규격을 넓히고(1부), 웹이 껍데기에게서 시험 자료를 넘겨받아 쓰고(2부), 팀이 시험 파일을 검사하고 서명해서 발행하는 도구를 만들어요(3부). 지시서 3장의 확정된 결정은 아래 일곱 가지이고 그대로 따라요.

1. 시험 자료는 정해진 주소 한 곳에서 받아요. 앱이 그 주소로 보내는 것은 없어요. 주소는 사람이 정해요.
2. 받는 일과 서명 확인은 껍데기(Swift)가 하고, 웹은 넘겨받은 자료를 검사해서 써요. 웹은 스스로 통신하지 않아요. 브라우저에서 단독으로 열면 묶음 안 시험만 써요.
3. 시험 날 자료는 준비되는 대로 나눠서 내요. 순서는 문항 구성과 배점(정답 공개 전), 정답, 유형 분류, 추정 등급컷, 성적 발표 뒤 자료예요.
4. 학생이 넣은 답과 표시는 어떤 경우에도 바꾸지 않아요. 점수, 등급, 계단은 지금의 시험 파일로 계산해요. 정답이 정정되면 다시 계산하고 바뀐 것을 학생에게 알려요.
5. "확정" 배지는 주관 기관이 원점수 등급컷을 직접 발표했을 때만 써요. 성적 발표 뒤에 업체가 계산한 값은 추정이에요.
6. 등급컷을 앱이 스스로 예측하지 않아요. 여러 기관 추정치의 가장 낮은 값과 가장 높은 값을 범위로 보여 줘요.
7. 풀이 잠금: 수능, 평가원 모의평가, 전국연합학력평가가 치러지는 시간에는 풀이 계열 기능을 보여 주지 않아요(지시서 4-5).

| answersNote 는 있으면 빈 글자나 빈칸뿐인 글자가 아니어야 하고, answersRev 가 2 이상이면 꼭 있어야 해요. answersRev 가 1이거나 칸이 없는데 answersNote 가 있어도 받아요 | 지시서 4-2. 학생에게 그대로 보이는 문장이라 비어 있으면 안 돼요. 정정 알림은 answersRev 가 2 이상일 때만 나오므로, 정정하기 전에 적어 둔 안내는 화면에 나오지 않아 막지 않았어요 |
| altAnswers 는 비어 있으면 오류예요(다른 정답이 없으면 칸을 빼요). 원소는 answer 와 같은 범위(5지선다는 1부터 보기 수까지, 단답형은 0~999)의 정수이고, answer 와 겹치거나 서로 겹치거나 answer 없이 altAnswers 만 있으면 오류예요 | 지시서 4-2. 빈 배열은 칸이 없는 것과 뜻이 같은데 글자가 달라서, 발행 도구가 채점에 영향을 주는 값이 바뀐 것으로 잘못 볼 수 있어요 |
| 모두 정답 처리(allCorrect: true) 문항은 정답을 공개한 뒤에도 answer 가 없어도 돼요. answer 와 altAnswers 를 함께 적어도 되고, 그때도 두 칸의 규칙을 그대로 검사해요. allCorrect 는 true 만 받아요. 인정하는 답 목록(acceptedAnswers)에는 넣지 않고 채점에서 따로 봐요 | 넣은 답과 상관없이 맞은 것으로 채점하므로 answer 가 없어도 채점할 수 있어요. 정정으로 모두 정답이 된 문항은 원래 정답을 남겨 둘 수 있게 했어요. true 만 받는 것은 지시서 4-2 그대로예요 |
| 등급컷 값은 0점부터 만점(문항 배점의 합)까지이고, 높은 등급(작은 번호)의 컷은 낮은 등급의 컷보다 낮을 수 없어요. 범위는 낮은 값끼리, 높은 값끼리 견주고 같은 값과 겹치는 범위는 받아요. 이 검사는 validateCutGrades(grades, total)로 내보내 시험 파일 검사와 발행 도구(exams:cuts)가 함께 써요. 배점을 읽을 수 없는 문항이 있으면 만점을 모르므로 위쪽 끝은 보지 않아요(그 문항의 오류로 이미 걸러져요). 확정 컷의 두 값이 같아야 한다는 검사는 시험 파일 검사에만 있어요 | 지시서 6-4의 exams:cuts 거부 조건을 시험 파일 검사와 한 벌로 두려고요(규칙을 두 벌로 만들지 않음). 기관마다 높은 등급의 컷이 낮지 않으면, 가장 낮은 값끼리와 가장 높은 값끼리도 그 순서가 지켜져요. 추정 범위는 서로 겹칠 수 있어서 막지 않았어요. 예시 시험 A, B의 컷은 그대로 통과해요 |
| 모양이 크게 틀린 시험 자료(시험 데이터가 배열, 문항이 객체가 아님, coords 가 배열이 아님, 좌표가 객체가 아님, 문항 번호를 글자로 바꿀 수 없음 등)에도 검사가 던지지 않고 오류 문장을 돌려줘요. 번호로 가리킬 수 없는 문항은 "3번째 문항"처럼 차례로 적어요. typeId 는 types 에 직접 적힌 유형만 받아요(constructor 같은 물려받은 이름을 거름). 그래도 검사 도중에 멈추면 "시험 데이터를 끝까지 검사하지 못했어요."로 통과시키지 않아요 | 2부에서 껍데기가 넘겨준 시험을 하나씩 검사해 틀린 것만 버리는데, 검사가 던지면 시험 목록 전체가 멈출 수 있어요. 1.1의 검사는 items 의 null, coords 의 null, 5, {} 에서 던졌고 typeId "constructor" 를 통과시켰어요 |
