## 9. 정답 노출

첫째, 차분 검사(e2e/leak.spec.ts). 배포하는 빌드와, 검산 예시에서 틀리는 6문항(11, 15, 20, 21, 27, 29번)의 정답만 다른 값으로 바꾼 검증용 빌드에 똑같은 조작을 했어요.
화면마다 보이는 글자, 숨은 글자, 모든 속성, 입력 칸 값, 가상 요소 글자를 통째로 견줘서, 한 글자라도 다르면 정답이 드러난 것으로 봐요.

판정에 쓰는 최소 기준: 통과한 단위 테스트 462개 이상(이번 462개, 건너뛴 것은 없어야 함), 화면 상태 374개 이상(이번 374개), 작은 화면 상태 133개 이상(이번 133개), 실제로 돈 화면 테스트 263개 이상(이번 263개), 요청 기록은 실제로 돈 화면 테스트마다 하나(이번 263개), 정답 노출은 화면을 읽는 검사 64번 이상(이번 64번)과 두 빌드를 견준 화면 25곳 이상(이번 25곳)과 대조 검사 4번 이상(이번 4번), 작은 화면에서 스크롤 없이 들어와야 하는 상태 68개 이상(이번 68개), 앱용 묶음 화면 테스트는 꼭 40개(이번 40개), 넘겨받기 화면 테스트는 꼭 22개(이번 22개)와 모양 비교 화면 테스트는 꼭 3개(이번 3개), 캡처는 묶음마다 79장, 통과한 발행 도구 단위 테스트 104개 이상(이번 104개)과 꼭 있어야 하는 발행 도구 테스트 44개, 테스트 전용 발행물 4가지(이번 기대대로 4가지). 검사가 줄거나 빠지거나 검사 기록에 결과 칸이 비어 있으면 해당 항목이 실패로 적혀요.

| 발행물 | 받는 쪽이 할 일(6-3) | exams:verify 에서 기대한 것 | 종료 코드 | 서명 | seq | 결과 |

## 자동으로 확인하지 못하는 것

- 실제 아이폰 Safari와 안드로이드 Chrome 기기에서의 동작과 터치 감각.
- 사람이 답 30개를 넣는 데 걸리는 시간과 남는 오입력. 사용성 테스트에서 재야 해요.
- 결과 화면을 학생이 바르게 읽는지. 사용성 테스트의 읽기 질문으로 확인해야 해요.
- 화면 낭독기(VoiceOver, TalkBack)로 실제로 들었을 때의 흐름.
- 아티팩트 뷰어 안에서의 동작. 뼈대와 비슷한 틀에 넣어 여는 것까지만 확인했어요.
- 아이폰 앱 껍데기(WKWebView) 안에서의 동작: 실제 다리, 햅틱의 느낌, 기기 글자 크기 설정, 길게 누르기와 화면 당김이 실제로 막히는지. 이 검증은 앱용 묶음을 가짜 다리를 넣은 Chromium(과 윈도우용 WebKit)에서만 확인해요. 아이폰 시뮬레이터의 확인은 맥의 ios/scripts/verify.sh 가 하고 결과는 docs/ios_검증결과.md 에 있어요.
- 아이폰 껍데기가 정해진 주소에서 시험 자료를 받아 서명과 sha256 을 확인하고 받는 쪽 규칙을 지키는지(작업 지시서 4). 이 검증은 발행 도구의 확인(exams:verify)과 테스트 전용 발행물까지만 봐요.
